# 코드 리뷰 규약

리뷰를 **쓰는 쪽과 받는 쪽** 모두의 규칙이다. PR 본문에 템플릿이 있는 것과 같은 이유로 리뷰에도 모양을 정한다. 누가 리뷰해도 받는 사람이 무엇을 해야 하는지 알 수 있게 하려는 것이다.

머지 방식, 필수 승인, PR 크기 같은 절차는 [CONTRIBUTING.md 3절](../../CONTRIBUTING.md)에 있다.

## 1. 리뷰 본문 구조

PR 전체에 다는 리뷰(요약 리뷰)는 아래 순서로 쓴다. 해당 없는 절은 지운다.

```markdown
한 줄 결론. 승인인지 수정 요청인지와 그 이유.

## [필수] 제목
고쳐야 머지할 수 있는 것.

## [질문] 제목
답을 들어야 판단할 수 있는 것.

## [제안] 제목
고려해 볼 만한 것. 안 고쳐도 머지한다.

## 좋았던 것
왜 좋은지 한 줄씩.

## 사소한 것
고치면 좋지만 안 고쳐도 되는 것.
```

줄 단위 지적은 해당 줄에 인라인 코멘트로 달고, 머리표(`[필수]`, `[질문]`, `[제안]`)를 앞에 붙인다.

**"좋았던 것"은 비워 두지 않는다.** 교육형 프로젝트라 지적만 받으면 다음에 같은 선택을 반복한다. 무엇이 왜 좋았는지 알아야 다시 한다. 좋은 게 정말 없으면 그 PR은 쪼개야 하는 PR이다.

## 2. 머리표

| 머리표 | 뜻 | 머지를 막는가 |
|---|---|---|
| `[필수]` | 고쳐야 한다 | 막는다 |
| `[질문]` | 답을 들어야 판단할 수 있다 | 막는다 |
| `[제안]` | 이렇게 하는 게 나아 보인다 | 막지 않는다 |
| `[사소]` | 오타, 링크 깨짐 같은 것 | 막지 않는다 |

**취향 차이를 `[필수]`로 쓰지 않는다.** `[필수]`는 보안 문제, 동작 오류, 규약 위반, 문서와 코드의 불일치에만 쓴다. "나는 이렇게 쓰는 게 좋다"는 `[제안]`이다.

## 3. 승인과 수정 요청

| 남은 것 | 리뷰 종류 |
|---|---|
| `[필수]`나 `[질문]`이 하나라도 있음 | **Request changes** |
| `[제안]`, `[사소]`만 있음 | **Approve** |
| 아직 판단할 수 없음 (더 봐야 함) | **Comment** |

`[제안]`이 여러 개 남아도 승인한다. 제안을 받아들일지는 작성자가 정한다.

승인한 뒤에 `[필수]`를 발견했으면 승인을 거두지 말고 코멘트로 남기고 머지를 기다려 달라고 적는다. 승인을 거두면 작성자가 무엇이 바뀐 건지 알기 어렵다.

## 4. 지적을 쓰는 방법

**무엇이 잘못되는지 구체적으로 쓴다.** "이거 위험해 보임"은 지적이 아니다. 어떤 입력이나 상황에서 무엇이 잘못되는지 적는다.

```markdown
나쁨: 권한 검사가 부족해 보입니다.

좋음: [필수] 다른 사용자의 글도 수정됩니다. `PUT /api/v1/posts/{id}`에서
작성자 확인 없이 바로 저장하므로, 로그인한 아무나 남의 글 ID를 넣으면
내용을 바꿀 수 있습니다. (A01, CWE-639)
```

**보안 지적에는 OWASP Top 10 2021과 CWE 번호를 붙인다.** 번호를 확인하지 않고 쓰지 않는다. OWASP Top 10 2021은 `A01`부터 `A10`까지다.

**확인한 것과 추측한 것을 구분한다.** 직접 확인한 지적은 어떻게 확인했는지 적는다. 확인하지 않았으면 `[필수]`가 아니라 `[질문]`으로 쓴다.

```markdown
좋음: SHA 8개를 `repos/{owner}/{repo}/commits/{tag}`와 대조해 전부 일치하는 것을 확인했다.

좋음: [질문] presigned PUT의 `Content-Length` 서명으로 크기가 실제로 막히는지
확인이 필요하다. 확인 방법: `size`를 1MB로 발급받고 20MB 파일을 PUT해서 403이 오는지 본다.
```

**원문을 유지한다.** 코드 식별자, 파일 경로, 로그, 오류 메시지는 번역하거나 고쳐 쓰지 않는다. 리뷰 글은 한국어로 쓴다.

## 5. 먼저 보는 것

위에서부터 본다.

1. **보안** — 인가 누락(IDOR), 인젝션, XSS, 시크릿 노출, 안전하지 않은 파일 업로드. 판단 기준은 [secure-coding.md](../security/secure-coding.md)
2. **동작 오류와 데이터 손실**
3. **하위 호환성** — API 응답 형식, DB 스키마. 기준은 [api.md](api.md)
4. **테스트** — 동작이 바뀌었는데 테스트가 없으면 지적한다. 권한이 걸린 API는 거부 케이스(비로그인 401, 다른 사용자 403 또는 404)가 있는지 본다
5. **문서** — 권한, 스키마, API, 운영 방식이 바뀌었으면 같은 PR에서 문서도 고쳤는지 본다

**스타일과 포매팅은 리뷰하지 않는다.** 린터와 포매터 몫이다. 린터가 잡지 못하는 것만 쓴다.

## 6. 보안 도구 경고

내 PR에 뜬 경고는 **작성자가 판별한다.** 진짜 취약점인지 오탐인지 판단해 근거를 PR 코멘트로 남긴다. 판별 방법과 억제 방법은 [tools.md](../security/tools.md)에 있다.

리뷰어는 작성자가 판별을 남겼는지 확인한다. 경고가 떴는데 아무 설명이 없으면 `[필수]`로 지적한다.

## 7. 스레드는 지적한 사람이 닫는다

레포 규칙이 **모든 대화 해결**을 요구한다. 미해결 스레드가 하나라도 있으면 머지가 막힌다.

| 스레드 | 닫는 사람 |
|---|---|
| 리뷰어가 남긴 지적 | 반영을 확인한 **리뷰어** |
| 보안 도구 봇이 남긴 경고 | 판별 근거를 적은 **작성자** |
| 작성자가 스스로 남긴 지적 | 반영한 **작성자** |

작성자가 리뷰어의 지적을 스스로 닫지 않는다. 반영했다고 생각한 것과 리뷰어가 요구한 것이 다를 수 있다.

## 8. 리뷰를 받는 쪽

- **새 커밋으로 반영한다.** force push로 덮어쓰지 않는다. 어차피 squash merge로 합쳐진다.
- **반영한 커밋 SHA와 무엇을 바꿨는지 스레드에 적는다.** 리뷰어가 다시 전체를 읽지 않아도 되게 한다.

```markdown
326d361에서 반영했습니다.

`tokens_valid_after` 초 단위 비교를 없애고 세션 ID(`sid`)로 바꿨습니다.
- 3-2-3 `login_sessions` 추가, `users.tokens_valid_after` 삭제
- 6-1 T3, T4 케이스 추가
```

- **동의하지 않으면 근거를 적고 반박한다.** 리뷰어가 틀릴 수 있다. 그냥 고치는 것보다 왜 지금 방식이 맞는지 적는 게 낫다. 그 대화가 다음 사람에게 남는다.
- **답을 모르면 묻는다.** 막혀 있는 것보다 낫다. 보안·백엔드는 PL, 인프라·통합은 PM이 창구다.
