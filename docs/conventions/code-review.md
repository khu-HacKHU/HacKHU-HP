# 코드 리뷰 규약

리뷰를 **쓰는 쪽과 받는 쪽** 모두의 규칙이다. PR 본문에 템플릿이 있는 것과 같은 이유로 리뷰에도 모양을 정한다. 누가 리뷰해도 받는 사람이 무엇을 해야 하는지 알 수 있게 하려는 것이다.

머지 방식, 필수 승인, PR 크기 같은 절차는 [CONTRIBUTING.md 3절](../../CONTRIBUTING.md)에 있다.

## 1. 리뷰 본문 구조

PR 전체에 다는 리뷰(요약 리뷰)는 아래 순서로 쓴다. 해당 없는 절은 지운다.

```markdown
한 줄 결론. 승인인지 수정 요청인지와 그 이유.

## P1 제목
사용자나 데이터에 피해가 가는 것.

## P2 제목
규약을 어기거나 운영에서 문제가 될 것.

## P3 제목
고려해 볼 만한 것. 안 고쳐도 머지한다.

## 좋았던 것
왜 좋은지 한 줄씩.
```

**지적은 요약 리뷰에 몰아 쓰지 말고 해당 줄에 인라인 코멘트로 하나씩 단다.** 하나의 코멘트에 하나의 지적만 담는다. 스레드가 지적 단위로 생겨서 반영과 해결을 따로 추적할 수 있다. 코멘트의 모양은 2절, 본문 쓰는 방법은 4절에 있다.

요약 리뷰의 `## P1`~`## P3` 절에는 인라인으로 달기 어려운 것(여러 파일에 걸친 문제, 설계 전체에 대한 지적)만 쓰고, 인라인으로 단 것은 제목만 한 줄씩 적어 둔다.

**"좋았던 것"은 비워 두지 않는다.** 교육형 프로젝트라 지적만 받으면 다음에 같은 선택을 반복한다. 무엇이 왜 좋았는지 알아야 다시 한다. 좋은 게 정말 없으면 그 PR은 쪼개야 하는 PR이다.

## 2. 결함 심각도 등급

**무엇을 고쳐야 하는지가 아니라 안 고치면 무슨 일이 생기는지로 등급을 정한다.**

| 등급 | 안 고치면 | 예 | 머지 |
|---|---|---|---|
| **P1** | 사용자나 데이터에 피해가 간다 | 인가 누락(IDOR), 인젝션, XSS, 시크릿 노출, 안전하지 않은 파일 업로드, 경합으로 중복 처리됨, 로그아웃·강등이 반영되지 않음, 데이터 손실 | **막는다** |
| **P2** | 지금은 안 터지지만 운영에서 문제가 된다 | 공통 규약 위반, 문서와 코드가 다름, 권한 거부 케이스 테스트가 없음, 교차 출처에서 필요한 헤더를 못 읽음, 테스트 케이스끼리 기대가 어긋남 | **막는다.** 후속 이슈로 합의하면 통과 |
| **P3** | 아무 일도 안 생긴다 | 더 단순한 구조 제안, 주석이 필요한 자리, 오타, 링크 깨짐 | 막지 않는다 |

**취향 차이를 P1이나 P2로 쓰지 않는다.** "나는 이렇게 쓰는 게 좋다"는 P3다. P1과 P2는 그렇게 둬서 생기는 결과를 한 문장으로 쓸 수 있을 때만 쓴다. 쓸 수 없으면 P3거나 지적이 아니다.

**질문은 등급과 함께 쓴다.** 답에 따라 결함일 수도 있는 것은 등급 뒤에 `[질문]`을 붙인다. 답을 듣기 전까지는 막는다. 확인이 필요하다는 뜻이고, 추측을 단정으로 쓰지 않으려는 것이다.

### 코멘트 맨 위에 등급 배지를 둔다

Codex가 쓰는 것과 같은 형식이다. 사람 리뷰와 AI 리뷰가 한 PR에 섞여도 등급을 바로 비교할 수 있다. 아래를 그대로 복사해 쓴다.

```markdown
<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-red?style=flat)</sub></sub>
```

```markdown
<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-orange?style=flat)</sub></sub>
```

```markdown
<sub><sub>![P3 Badge](https://img.shields.io/badge/P3-yellow?style=flat)</sub></sub>
```

배지 다음에 빈 줄을 하나 두고 본문을 쓴다. 질문이면 배지 옆에 `<sub>[질문]</sub>`을 붙인다.

```markdown
<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-red?style=flat)</sub></sub> <sub>[질문]</sub>

presigned PUT의 `Content-Length` 서명으로 크기가 실제로 막히는지 확인이 필요합니다. ...
```

배지는 외부 이미지라 안 보이는 환경이 있다. 그럴 때는 `P1`처럼 글자만 적어도 된다. 등급이 전달되는 게 목적이고 배지는 거기에 얹는 것이다.

## 3. 승인과 수정 요청

| 남은 것 | 리뷰 종류 |
|---|---|
| P1이 하나라도 있음 | **Request changes** |
| P2만 있음 | **Request changes.** 후속 이슈를 만들어 합의하면 Approve |
| P3만 있음 | **Approve** |
| 아직 판단할 수 없음 (더 봐야 함) | **Comment** |

P3가 여러 개 남아도 승인한다. 받아들일지는 작성자가 정하고, 스레드도 작성자가 닫는다. (7절)

P2를 후속 이슈로 넘길 때는 이슈 번호를 스레드에 적는다. "나중에 고치자"만 적으면 아무도 안 고친다.

승인한 뒤에 P1을 발견했으면 승인을 거두지 말고 코멘트로 남기고 머지를 기다려 달라고 적는다. 승인을 거두면 작성자가 무엇이 바뀐 건지 알기 어렵다.

### 라운드 상한

**라운드가 3회를 넘으면 P1만 그 PR에서 고치고, P2와 P3는 후속 이슈로 넘기고 머지한다. 리뷰가 길어질수록 지적의 가치는 떨어지고 머지가 늦어지는 비용은 커진다.**

작성자가 반영 커밋을 올리고 리뷰어가 다시 보는 것을 한 라운드로 센다. 새 커밋이 올라오면 기존 승인이 자동으로 해제되므로(`dismiss_stale_reviews_on_push`), 라운드마다 리뷰어가 다시 봐야 한다. 그래서 상한이 필요하다.

라운드가 길어지는 PR은 대개 너무 큰 PR이다. 3회에 닿았으면 남은 지적을 이슈로 넘기면서 PR을 쪼갤 수 있는지도 같이 본다.

## 4. 지적을 쓰는 방법

지적 하나의 본문은 네 부분으로 쓴다. Codex가 쓰는 순서와 같다.

1. **무엇이 잘못되는가** — 한 문장
2. **예를 들어** — 그 일이 실제로 일어나는 경로. 입력, 순서, 조건을 적는다
3. **무엇과 어긋나는가** — 어떤 문서, 사용자 스토리, 규약과 충돌하는지
4. **무엇을 해 달라** — 요청. 보안이면 `(CWE-xxx)`를 끝에 붙인다

```markdown
<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-red?style=flat)</sub></sub>

작성자 확인 없이 저장하므로 다른 사용자의 글도 수정됩니다.
예를 들어 `MEMBER` 역할로 로그인한 뒤 `PUT /api/v1/posts/42`에 남의 글 ID를
넣으면 본문이 그대로 바뀝니다. 공지는 운영진만 수정할 수 있어야 한다는
게시판 사용자 스토리 2절과 충돌합니다. 저장 전에 `author_id`와 현재 사용자를
비교하고, 다른 사용자로 수정이 거부되는 테스트를 추가해 주세요. (A01, CWE-639)
```

"이거 위험해 보입니다"는 지적이 아니다. 2번이 없으면 받는 사람이 무엇을 재현해야 할지 모르고, 4번이 없으면 무엇을 해야 끝인지 모른다.

**보안 지적에는 OWASP Top 10 2021과 CWE 번호를 붙인다.** 번호를 확인하지 않고 쓰지 않는다. OWASP Top 10 2021은 `A01`부터 `A10`까지다.

**확인한 것과 추측한 것을 구분한다.** 직접 확인한 지적은 어떻게 확인했는지 적는다. 확인하지 않았으면 단정하지 말고 `[질문]`을 붙인다.

```markdown
확인한 것: SHA 8개를 `repos/{owner}/{repo}/commits/{tag}`와 대조해 전부 일치하는 것을 확인했습니다.

확인하지 않은 것:
<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-red?style=flat)</sub></sub> <sub>[질문]</sub>

presigned PUT의 `Content-Length` 서명으로 크기가 실제로 막히는지 확인이 필요합니다.
`size`를 1MB로 발급받고 20MB 파일을 PUT해서 403이 오는지 봐 주세요. 안 막히면
10MB 제한이 rate limit 하나만 남아, 사용자당 시간당 100장이 전부 1GB가 될 수 있습니다.
```

**원문을 유지한다.** 코드 식별자, 파일 경로, 로그, 오류 메시지는 번역하거나 고쳐 쓰지 않는다. 리뷰 글은 한국어로 쓴다.

## 5. 먼저 보는 것

위에서부터 본다.

1. **보안** — 인가 누락(IDOR), 인젝션, XSS, 시크릿 노출, 안전하지 않은 파일 업로드. 판단 기준은 [secure-coding.md](../security/secure-coding.md)
2. **동작 오류와 데이터 손실**
3. **하위 호환성** — API 응답 형식, DB 스키마. 기준은 [api.md](api.md)
4. **테스트** — 동작이 바뀌었는데 테스트가 없으면 지적한다. 권한이 걸린 API는 거부 케이스(비로그인 401, 다른 사용자 403 또는 404)가 있는지 본다
5. **문서** — 권한, 스키마, API, 운영 방식이 바뀌었으면 같은 PR에서 문서도 고쳤는지 본다

**스타일과 포매팅은 리뷰하지 않는다.** 린터와 포매터 몫이다. 린터가 잡지 못하는 것만 쓴다.

## 6. 보안 도구 경고

내 PR에 뜬 경고는 **작성자가 판별한다.** 진짜 취약점인지 오탐인지 판단해 근거를 PR 코멘트로 남긴다. 판별 방법과 억제 방법은 [tools.md](../security/tools.md)에 있다.

리뷰어는 작성자가 판별을 남겼는지 확인한다. 경고가 떴는데 아무 설명이 없으면 P2로 지적한다. 판별해 보니 진짜 취약점이면 그 자체가 P1이다.

## 7. 스레드는 지적한 사람이 닫는다

레포 규칙이 **모든 대화 해결**을 요구한다. 미해결 스레드가 하나라도 있으면 머지가 막힌다.

| 스레드 | 닫는 사람 |
|---|---|
| 리뷰어가 남긴 P1·P2 | 반영을 확인한 **리뷰어** |
| 리뷰어가 남긴 P3 | **작성자.** 받아들이든 안 받아들이든 닫을 수 있다 |
| 보안 도구 봇이 남긴 경고 | 판별 근거를 적은 **작성자** |
| 작성자가 스스로 남긴 지적 | 반영한 **작성자** |

**P1과 P2는 작성자가 스스로 닫지 않는다.** 반영했다고 생각한 것과 리뷰어가 요구한 것이 다를 수 있다.

**P3는 작성자가 닫는다.** P3는 막지 않는 등급인데, 인라인으로 달면 스레드가 생겨 대화 해결 규칙 때문에 실제로는 막힌다. 그 모순을 없애려고 닫을 권한을 작성자에게 둔다. 받아들이지 않고 닫을 때는 한 줄로 이유를 남긴다. 리뷰어가 그게 P3가 아니라고 생각하면 등급을 올려 다시 달면 된다.

리뷰어가 머지를 막지 않으면서 P3를 남기고 싶으면, 인라인 대신 요약 리뷰의 `## P3` 절에 적어도 된다. 스레드가 생기지 않는다.

## 8. 리뷰를 받는 쪽

- **새 커밋으로 반영한다.** force push로 덮어쓰지 않는다. 어차피 squash merge로 합쳐진다.
- **반영한 커밋 SHA와 무엇을 바꿨는지 스레드에 적는다.** 리뷰어가 다시 전체를 읽지 않아도 되게 한다.

```markdown
326d361에서 반영했습니다.

`tokens_valid_after` 초 단위 비교를 없애고 세션 ID(`sid`)로 바꿨습니다.
- 3-2-3 `login_sessions` 추가, `users.tokens_valid_after` 삭제
- 6-1 T3, T4 케이스 추가
```

- **동의하지 않으면 근거를 적고 반박한다.** 리뷰어가 틀릴 수 있다. 그냥 고치는 것보다 왜 지금 방식이 맞는지 적는 게 낫다. 그 대화가 다음 사람에게 남는다.
- **답을 모르면 묻는다.** 막혀 있는 것보다 낫다. 보안·백엔드는 PL, 인프라·통합은 PM이 창구다.
