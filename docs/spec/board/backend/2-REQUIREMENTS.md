# 2 요구사항

본 문서는 프론트엔드가 게시판 백엔드에 기대하는 것을 측정할 수 있는 값으로 정한다.

<br>

### 2-1. 글의 길이

| 항목 | 값 |
|---|---|
| 제목 | 앞뒤 공백을 지운 뒤 1자 이상 100자 이하 |
| 본문 | 1자 이상 10,000자 이하 <br> 공백과 줄바꿈만으로 된 본문은 받지 않음 |

- 사용자 스토리가 길이 제한을 게시판팀에 맡겼다. (USER-STORIES.md 1절)
- 글자 수는 유니코드 코드 포인트 단위로 센다. 한글 한 자와 영문 한 자를 같은 한 자로 센다.
- 10,000자는 A4 약 5장 분량이다. 운영 중에 모자라면 늘린다.
- 세 게시판이 같은 값을 쓴다. 자료게시판은 긴 내용을 첨부파일로 올리므로 본문을 더 늘릴 이유가 없다고 본다.

<br>

### 2-2. 목록

| 항목 | 값 |
|---|---|
| 정렬 | 작성 시각이 최신인 글부터 <br> 작성 시각이 같으면 ID가 큰 글부터 |
| 페이지 크기 | 기본 20개 <br> 1개부터 20개까지 요청할 수 있음 <br> 20개를 넘게 요청하면 20개로 맞춤 |
| 페이지 번호 | 0부터 |
| 목록에 주는 것 | 제목, 작성자, 작성 시각, 수정 시각 <br> 자료게시판은 첨부파일 수도 줌 <br> 본문과 첨부파일 목록은 주지 않음 |

- 세 게시판 목록이 같은 규칙을 쓴다.
- 게시판 목록 화면은 사용자 스토리대로 한 페이지에 20개를 보여 준다. (USER-STORIES.md 1절)
- 메인 화면은 최신 공지 5개만 보여 준다. 그래서 페이지 크기를 줄여 요청할 수 있게 한다. 메인 화면은 갤러리팀이 만들고 공지 목록 API를 쓴다. (홈 USER-STORIES.md 1절, 제품 DECISIONS.md D12, PR #102)
- 정렬은 클라이언트가 바꿀 수 없다. 최신순이 아닌 정렬을 요청하면 거부한다. ([4-2-INTERACTION-CONTRACT.md](4-2-INTERACTION-CONTRACT.md))
- 페이지 크기 상한 20은 레포 전역 설정(최대 100)보다 좁다. 전역 설정으로는 걸리지 않으므로 코드에서 직접 맞춘다. ([5-1-QUALITY-SECURITY.md](5-1-QUALITY-SECURITY.md) 5-1-5)
- 페이지 크기 상한 20은 레포 전역 설정(최대 100)보다 좁다. 전역 설정으로는 걸리지 않으므로 코드에서 직접 맞춘다. ([5-1-QUALITY-SECURITY.md](5-1-QUALITY-SECURITY.md) 5-1-5)
- 마지막 페이지를 넘는 번호를 요청하면 빈 목록을 준다. 오류로 다루지 않는다.

<br>

### 2-3. 첨부파일

값은 사용자 스토리가 기준이다. (USER-STORIES.md 4절)

| 항목 | 값 |
|---|---|
| 허용 형식 | pdf, docx, pptx, xlsx |
| 파일 하나의 최대 크기 | 20MB (20,971,520바이트) |
| 글 하나의 최대 첨부 수 | 5개 <br> 첨부 없이도 글을 쓸 수 있음 |
| 원래 파일 이름 | 확장자를 포함해 1자 이상 200자 이하 |
| 업로드 주소 만료 | 발급 뒤 10분 |
| 다운로드 주소 만료 | 발급 뒤 10분 |

- 업로드 주소 10분은 갤러리와 같은 값이다. 20MB를 학교 와이파이로 올려도 넉넉하다고 본다. ([gallery 2-REQUIREMENTS](../../gallery/backend/2-REQUIREMENTS.md))
- 다운로드 주소는 사용자 스토리의 "링크를 받은 지 10분이 지나면 열리지 않음"을 따른다. 다운로드는 주소를 받은 직후 시작한다고 보고, 10분 안에 시작한 다운로드가 끝까지 받아지는지는 S3 동작을 따른다.
- 원래 파일 이름 200자는 게시판팀이 정한 값이다. 객체 키에 쓰지 않으므로 화면과 내려받을 때의 이름에만 영향이 있다.

<br>

### 2-4. 응답 시간

| API | 목표 (p95) |
|---|---|
| 목록, 상세 (세 게시판) | 300ms 이하 |
| 글 작성, 수정, 삭제 (첨부 없음) | 300ms 이하 <br> 인증 처리 20ms 포함 ([auth 2-3](../../auth/backend/2-REQUIREMENTS.md)) |
| 업로드 주소 발급 | 500ms 이하 <br> 서명은 서버 안에서 하고 S3를 부르지 않음 |
| 첨부가 있는 자료게시판 글 작성, 수정 | 1초 이하 <br> 새 첨부파일마다 S3에서 앞부분을 읽어 형식을 확인함 (최대 5번) |
| 첨부가 있는 자료게시판 글 삭제 | 1초 이하 <br> S3 객체 삭제 포함 |
| 다운로드 주소 발급 | 300ms 이하 |

동아리 규모(가입자 수백 명, 글 수천 건)를 가정한다. 별도 성능 테스트는 두지 않는다.

<br>

### 2-5. 처리량과 요청 제한

동시 사용자가 적어 처리량 목표는 두지 않는다.

| API | 제한 | 이유 |
|---|---|---|
| 업로드 주소 발급 | 사용자 ID당 1분에 5번, 1시간에 파일 50개 | 확정하지 않은 업로드로 저장 공간을 채우는 것을 막음 <br> 갤러리와 같은 방식, 파일 수는 글 하나 5개 기준으로 줄임 |
| 다운로드 주소 발급 | 사용자 ID당 1분에 30번 | 주소를 대량으로 받아 외부에 퍼뜨리는 것을 늦춤 |
| 그 밖의 게시판 API | 두지 않음 | 쓰기는 동아리원 이상만 할 수 있고, 공개 조회는 페이지 크기로 제한함 |

- 한도를 넘으면 429와 `Retry-After`를 준다.
- 카운터는 서버 메모리에 둔다. 인증권한, 갤러리와 같은 방식이다. ([auth DECISIONS.md](../../auth/backend/DECISIONS.md) A11)

<br>

### 2-6. 반영 시점

| 변경 | 반영 시점 |
|---|---|
| 글 작성, 수정 | 성공 응답을 받은 뒤의 다음 조회부터 |
| 글 삭제 | 성공 응답을 받은 뒤의 다음 조회부터 404 |
| 첨부파일 삭제 (글 수정이나 글 삭제) | 성공 응답 뒤로는 다운로드 주소를 새로 발급할 수 없음 <br> 이미 발급한 주소는 S3 객체가 지워져 열리지 않음 |
| 작성자나 요청한 사람의 역할 변경, 탈퇴 | 다음 요청부터 ([auth 2-2](../../auth/backend/2-REQUIREMENTS.md)) |

게시판 응답에는 서버 캐시를 두지 않는다.

<br>

### 2-7. 보존 기간과 데이터 수명

| 데이터 | 수명 |
|---|---|
| 글 | 작성자나 관리자가 지울 때까지 <br> 자동으로 지우지 않음 |
| 지운 글 | 삭제 즉시 행을 지움 <br> 복구하지 않음 |
| 첨부파일 (DB 행과 S3 객체) | 글을 지우거나 글 수정에서 뺄 때 함께 지움 |
| 확정하지 않은 업로드 | 업로드 주소가 만료된 뒤 `global/storage`의 정리 작업이 지움 ([gallery 3-2](../../gallery/backend/3-2-DESIGN-DB-SCHEMA.md)) |
| 탈퇴한 작성자의 글과 첨부파일 | 지우지 않고 남김 <br> 작성자는 "탈퇴한 회원"으로 보여 줌 |
