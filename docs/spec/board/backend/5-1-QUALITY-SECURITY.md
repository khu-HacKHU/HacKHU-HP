# 5-1 보안

본 문서는 게시판 API의 인증 수준과 권한 규칙, 입력 검증, 첨부파일 업로드와 다운로드, 개인정보와 위협 모델을 정한다. 공통 규칙은 시큐어 코딩 규칙을 따른다. ([secure-coding.md](../../../security/secure-coding.md))

<br>

### 5-1-1. 인증 수준

인증 수준의 정의는 인증권한 세트를 따른다. ([auth 5-1-1](../../auth/backend/5-1-QUALITY-SECURITY.md))

| 수준 | 통과하는 사람 |
|---|---|
| 공개 | 누구나 |
| 동아리원 | 역할이 `MEMBER` 이상 |
| 운영진 | 역할이 `STAFF` 이상 |
| 관리자 | 역할이 `ADMIN` |

- 승인 대기 회원(`PENDING`)은 방문자와 같다. 게시판에서는 공지 목록과 상세만 통과한다.
- 공지 목록과 상세만 Security 설정의 공개 목록에 `GET` 메서드로 적는다. 같은 경로의 `POST`, `PUT`, `DELETE`와 자유게시판, 자료게시판 경로는 공개 목록에 넣지 않는다. Security 설정의 기본값이 동아리원 이상이므로 자유게시판과 자료게시판은 따로 적지 않아도 막힌다. ([auth 3-1](../../auth/backend/3-1-DESIGN-SOFTWARE-ARCHITECTURE.md))
- 다른 기능의 API에 `hasRole('PENDING')`, `authenticated()`를 쓰지 말라는 인증권한 세트의 규칙을 따른다. 승인 대기 회원이 동아리원 기능을 통과하기 때문이다.

<br>

| 자료게시판 삭제 | 동아리원 | 글의 `board_type`이 `ARCHIVE`인지 <br> 5-1-3의 작성자 규칙 |

| 첨부 다운로드 주소 발급 | 동아리원 | 글의 `board_type`이 `ARCHIVE`인지 <br> 첨부가 그 글의 것인지 <br> 요청 횟수 제한 |

### 5-1-3. 권한 규칙

**글 작성** (USER-STORIES.md 1절)

- 공지는 운영진 이상, 자유게시판과 자료게시판은 동아리원 이상이 쓴다.
- 작성자는 access 토큰으로 정한 현재 사용자의 ID다. 요청 본문, 쿼리, 헤더에서 받지 않는다.

**글 수정과 삭제** (USER-STORIES.md 1절, 2절)

| 게시판 | 관리자 (`ADMIN`) | 그 밖의 사람 |
|---|---|---|
| 공지 | 모든 공지 | 운영진(`STAFF`)이면서 글의 `author_id`가 현재 사용자의 ID와 같음 |
| 자유게시판, 자료게시판 | 모든 글 | 동아리원 이상이면서 글의 `author_id`가 현재 사용자의 ID와 같음 |

- 작성자 확인은 현재 사용자 ID와 DB에서 읽은 `author_id`를 비교한다. 요청에 담긴 작성자 정보를 믿지 않는다. (CWE-639)
- 운영진에서 동아리원으로 내려간 사람은 자기가 쓴 공지도 고치거나 지울 수 없다. 공지 쓰기가 운영진의 권한이기 때문이다. 이 공지는 관리자가 관리한다. 근거는 사용자 스토리 1절 상황표의 "권한이 없는 사람은 다른 방법으로 시도해도 막힘"이다. (USER-STORIES.md 1절, [DECISIONS.md](DECISIONS.md) B4)
- 자유게시판과 자료게시판에서는 이런 경우가 없다. 동아리원 아래로 내리는 역할 변경이 없고, 탈퇴한 계정은 로그인할 수 없기 때문이다. (auth 5-1-3)
- 관리자가 남의 자료게시판 글을 고칠 때 첨부를 빼거나 더할 수 있다. 새로 더한 첨부는 관리자가 올린 업로드여야 한다. (5-1-8)

**검사 순서**

1. 인증 수준을 확인한다. 토큰이 없거나 무효면 401, 역할이 부족하면 403 `FORBIDDEN`.
2. `id`와 게시판 종류로 글을 읽는다. 없으면 404 `POST_NOT_FOUND`.
3. 수정과 삭제는 작성자 규칙을 확인한다. 통과하지 못하면 403 `POST_FORBIDDEN`.

- 1단계를 글을 찾기 전에 하므로, 방문자와 승인 대기 회원은 자유게시판, 자료게시판 글 ID가 있든 없든 같은 응답을 받는다. 동아리원이 아닌 사람에게 글이 있는지 알려 주지 않는다. (USER-STORIES.md 3절, [DECISIONS.md](DECISIONS.md) B7)
- 3단계에서 남의 글이면 404가 아니라 403을 준다. 3단계까지 온 사람은 동아리원이라 그 글을 볼 수 있으므로 존재를 숨길 이유가 없다.
- 다른 게시판 글은 2단계에서 그 게시판 글이 아닌 것으로 걸러져 404가 된다.

### 5-1-4. 게시판 종류 구분

세 게시판이 `post` 테이블 하나를 같이 쓴다. ([3-2-DESIGN-DB-SCHEMA.md](3-2-DESIGN-DB-SCHEMA.md)) 공지는 공개, 나머지는 동아리원 전용이라 섞이면 동아리원 전용 글이 공개된다.

- 모든 글 조회, 수정, 삭제 쿼리는 조건에 `board_type`을 넣는다. `id`만으로 글을 읽은 뒤 애플리케이션에서 종류를 비교하지 않는다.
- 저장소는 `id`만으로 읽는 메서드(`findById`)를 열지 않는다. 게시판 종류를 받는 메서드만 둔다.
- `board_type`은 요청에서 받지 않는다. 게시판마다 있는 컨트롤러가 정한 값을 서비스에 넘긴다.
- 첨부파일은 글을 거쳐서만 찾는다. 다운로드 주소 발급은 `postId`와 `ARCHIVE`로 글을 읽은 뒤 그 글의 첨부 중에서 `attachmentId`를 찾는다.

테스트로 아래를 확인한다.

| 부른 API | 넣은 ID | 기대 |
|---|---|---|
| 공지 상세 | 자유게시판 글, 자료게시판 글 | 404 |
| 자유게시판 상세, 수정, 삭제 | 공지, 자료게시판 글 | 404 |
| 자료게시판 상세, 수정, 삭제 | 공지, 자유게시판 글 | 404 |
| 다운로드 주소 발급 | 다른 자료게시판 글의 첨부 ID | 404 |

### 5-1-5. 입력 검증

- 글 요청 DTO는 `title`, `content`와 자료게시판의 `attachmentIds`, `uploadIds`만 가진다. `id`, `authorId`, `boardType`, `createdAt`, `updatedAt`, `objectKey`가 없다. (CWE-915)
- `title`은 앞뒤 공백을 지운 뒤 길이를 검사한다. 제어 문자와 양방향 텍스트 제어 문자(U+202A~U+202E, U+2066~U+2069)를 거부한다. 제목은 목록에서 다른 글과 나란히 보이므로 글자 방향을 뒤집어 다른 글처럼 보이게 하는 것을 막는다.
- `content`는 줄바꿈(`\n`)과 탭을 뺀 제어 문자를 거부한다. 특히 NUL(U+0000)은 PostgreSQL `TEXT`에 저장할 수 없어서 검사하지 않으면 500이 난다.
- 길이는 코드 포인트 단위로 센다. (3-2-DESIGN-DB-SCHEMA.md 3-2-2)
- 길이 검사를 통과하지 못하면 400 `INVALID_INPUT`과 필드별 사유를 준다. 사유에 입력값을 다시 넣지 않는다.
- 요청 본문 전체 크기는 64KB까지 받는다. 본문 10,000자가 UTF-8로 최대 40KB이므로 정상 요청은 넉넉히 들어간다. 큰 본문을 보내 서버 메모리를 쓰게 하는 것을 막는다.
  - Spring MVC와 Tomcat에는 JSON 본문 크기를 막는 기본 설정이 없다. `server.tomcat.max-http-form-post-size`는 폼 요청에만 적용된다. 그래서 직접 건다.
  - `Content-Length`만 보면 `Transfer-Encoding: chunked` 요청이 빠져나간다. 읽은 바이트를 세다가 넘으면 끊는 방식이어야 한다.
  - 거는 방법(필터 위치, 게시판에만 걸지 전역으로 걸지)은 첫 쓰기 API인 #32에서 정한다. 전역으로 걸면 다른 팀 API에도 영향이 있어 PL과 정한다.
- 경로의 ID와 쿼리의 `page`, `size`는 정수만 받는다. `size`는 20을 넘으면 20으로 맞춘다.
  - 전역 설정(`spring.data.web.pageable.max-page-size: 100`)은 100으로 자르므로 20 상한은 걸리지 않는다. `Pageable`을 그대로 쓰지 않고 서비스가 `Math.min(size, 20)`으로 직접 맞춘다.
- `sort`는 허용 목록(`createdAt,desc` 하나)으로 먼저 검사하고, 맞지 않으면 쿼리를 실행하기 전에 400으로 거부한다. 받은 값을 쿼리에 넘기지 않고 서버가 고정한 정렬만 건다. 없는 필드를 그대로 넘기면 500과 ERROR 로그가 생기기 때문이다. (CWE-89)
- `uploadIds`는 UUID 형식만 받는다. `attachmentIds`는 1 이상의 정수만 받는다. 두 배열 모두 같은 값이 두 번 나오면 400이다.

### 5-1-6. 원래 파일 이름

원래 파일 이름은 사용자가 정한 값이라 그대로 믿지 않는다. 화면에 보이고, 내려받을 때 파일 이름이 되기 때문이다.

- 객체 키에 쓰지 않는다. 객체 키는 서버가 `board/{uuid}.{확장자}`로 만든다. 경로 이동(`../`)이나 다른 파일 덮어쓰기를 막는다. (CWE-22)
- 저장하기 전에 경로 부분(`/`, `\` 앞)을 지운다. 브라우저에 따라 전체 경로가 오는 경우가 있다.
- 제어 문자(줄바꿈 포함)와 양방향 텍스트 제어 문자를 거부한다. 줄바꿈은 `Content-Disposition` 헤더를 깨뜨려 다른 헤더를 끼워 넣을 수 있고(CWE-113), 양방향 문자는 `문서.pdf`처럼 보이는 다른 확장자 파일을 만들 수 있다(예: `fdp.exe`를 뒤집어 보이게 함).
- 확장자는 마지막 `.` 뒤로 판단하고 대소문자를 무시한다. `보고서.pdf.exe`는 확장자가 `exe`라서 거부된다.
- 내려받을 때 파일 이름은 RFC 6266, RFC 5987 형식(`filename*=UTF-8''...`)으로 인코딩해 서명에 넣는다. 한글 이름이 깨지지 않고 헤더에 특수 문자가 그대로 들어가지 않는다.

### 5-1-7. 업로드와 형식 확인

파일 바이트는 서버를 거치지 않고 presigned PUT으로 S3에 직접 올라간다. (secure-coding.md 5절) 형식과 크기는 세 단계로 확인한다.

| 단계 | 확인 | 막는 것 |
|---|---|---|
| 1. 발급 요청 | 확장자, `contentType`, `size`가 허용 값이고 서로 짝이 맞는지 | 허용하지 않는 형식과 20MB 초과를 S3에 올리기 전에 거부 |
| 2. 업로드 | 서명에 `Content-Type`과 정확한 `Content-Length`가 들어감 | 신고와 다른 형식 헤더, 신고보다 큰 파일 |
| 3. 글에 확정 | S3에서 파일 앞 8바이트를 읽어 실제 형식 확인 | 확장자와 헤더만 바꾼 다른 형식 파일 |

3단계 판정은 아래와 같다.

| 신고한 형식 | 파일 앞부분 | 판정 |
|---|---|---|
| pdf | `%PDF-` (`25 50 44 46 2D`) | 통과 |
| docx, pptx, xlsx | `PK\x03\x04` (`50 4B 03 04`) | 통과 |
| 그 밖의 조합 | | 거부, 객체 삭제, 400 `POST_INVALID_UPLOAD` |

**docx, pptx, xlsx의 남는 위험**

세 형식은 안쪽이 zip이라 파일 앞부분만으로는 진짜 문서인지, 확장자만 바꾼 zip인지 구분할 수 없다. (D8) 이 세트는 zip 안의 구조(`[Content_Types].xml` 등)까지는 확인하지 않는다. ([DECISIONS.md](DECISIONS.md) B9)

- 확인하려면 서버가 파일 전체(최대 20MB, 글 하나에 5개)를 내려받아 압축을 풀어 봐야 한다. 압축 폭탄(작은 zip이 풀면 수 GB가 되는 파일) 대응까지 새로 필요해진다.
- 대신 피해를 줄이는 장치를 둔다.
  - 첨부는 동아리원만 올리고 동아리원만 받는다. 올린 사람이 로그로 남는다. (5-1-12)
  - 다운로드는 항상 `Content-Disposition: attachment`로 내려 브라우저가 열거나 실행하지 않는다. (5-1-9)
  - 다운로드 응답의 `Content-Type`은 저장한 형식으로 고정한다.
  - S3 버킷은 공개 접근을 막고 presigned URL로만 오간다.
- 남는 위험: 동아리원이 문서인 척한 zip(안에 실행 파일)을 올리면 다른 동아리원이 받아서 직접 열 수 있다. 실행은 받은 사람이 직접 해야 하므로 받아들이고, 신고가 들어오면 관리자가 글을 지운다.

**발급과 확정의 연결**

- 업로드 발급 기록에 요청한 사람 ID, 용도(`BOARD_ATTACHMENT`), 형식, 크기, 원래 파일 이름, 만료 시각을 남긴다. 클라이언트에는 `uploadId`만 준다. (gallery 1-BACKGROUND.md 3절)
- 확정할 때 클라이언트가 보낸 값이 아니라 발급 기록의 값으로 첨부 행을 만든다. 확정 요청에서 형식이나 크기를 다시 받지 않는다.

### 5-1-8. 첨부 확정과 동시 요청

**확정 순서** (자료게시판 작성과 수정)

1. 글 수정이면 글 행을 `FOR UPDATE`로 잠그고 작성자 규칙을 확인한다.
2. 각 `uploadId`의 발급 기록이 현재 사용자에게, `BOARD_ATTACHMENT` 용도로 발급되었고, 아직 쓰이지 않았고, 만료되지 않았는지 확인한다. 하나라도 아니면 전체를 거부한다.
3. 통과한 업로드마다 S3에서 앞 8바이트를 읽어 형식을 확인한다 (5-1-7). 하나라도 실패하면 전체를 거부한다.
4. 발급 기록을 조건부 갱신으로 사용 처리한다. `WHERE status = 'ISSUED' AND user_id = :userId AND expires_at > now()`로 갱신하고 갱신된 행 수가 요청 수와 다르면 전체를 롤백한다. 같은 `uploadId`를 두 요청이 동시에 써도 하나만 성공한다.
5. 남길 첨부, 뺄 첨부, 새 첨부를 정리하고 개수가 5개 이하인지 센다. 글 행을 잠근 상태라 두 수정 요청이 동시에 와도 6개가 되지 않는다.
6. 커밋한 뒤 뺀 첨부의 S3 객체를 지운다.

- 2~3단계에서 거부되면 그 요청의 업로드는 모두 사용 처리하고 S3 객체를 지운다. 같은 `uploadId`로 계속 형식 확인을 시도해 S3 읽기 비용을 쓰게 하는 것을 막는다. 갤러리와 같은 방식이다. ([gallery 4-2](../../gallery/backend/4-2-INTERACTION-CONTRACT.md) 4절)
- 3단계의 S3 읽기는 잠금을 잡은 채로 한다. 첨부가 많아야 5개이고 읽는 양이 8바이트라 짧다고 본다. 길어지면 5-2에서 잠금 밖으로 옮긴다.
- 나머지 동시성 처리는 5-2에서 정한다.

### 5-1-9. 다운로드

- 다운로드 주소는 요청할 때마다 새로 서명한다. 만료는 10분이다. (USER-STORIES.md 4절)
- 서명에 응답 헤더 덮어쓰기를 넣는다. `response-content-disposition`은 `attachment; filename*=UTF-8''{인코딩한 원래 파일 이름}`, `response-content-type`은 저장한 형식이다. 클라이언트가 주소의 쿼리를 바꾸면 서명이 깨져 S3가 거부한다.
- 상세 응답에 다운로드 주소를 넣지 않는다. 상세를 볼 때마다 주소가 발급되면 화면 캐시, 브라우저 기록, 프록시 로그에 유효한 주소가 남는다. 받기를 누를 때만 `POST`로 발급한다. ([DECISIONS.md](DECISIONS.md) B6)
- 주소를 다른 사람에게 넘기면 10분 동안은 받을 수 있다. 사용자 스토리가 정한 범위이고, 그 뒤로는 열리지 않는다.

<br>

### 5-1-10. 출력과 XSS

- 서버는 제목, 본문, 원래 파일 이름을 받은 글자 그대로 저장하고 JSON으로 준다. HTML 이스케이프나 태그 제거를 저장할 때 하지 않는다. 저장 단계에서 바꾸면 다른 화면에서 두 번 이스케이프되거나, 거르는 규칙을 우회하는 입력이 생기기 때문이다.
- XSS는 출력 단계에서 막는다. 프론트엔드는 제목, 본문, 파일 이름을 글자로 출력하고 HTML로 해석하지 않는다. (CWE-79, [secure-coding.md](../../../security/secure-coding.md) 4절)
- 응답은 `Content-Type: application/json`이다. 브라우저가 게시판 응답을 HTML로 해석하지 않는다.
- 첨부파일은 HTML이나 SVG를 받지 않으므로 S3 주소에서 스크립트가 실행되지 않는다. 다운로드는 `attachment`로만 내려 PDF도 브라우저가 열지 않는다.

### 5-1-11. 개인정보

| 정보 | 응답에 넣는 곳 | 볼 수 있는 사람 |
|---|---|---|
| 작성자 ID, 이름 | 목록, 상세 | 공지는 누구나, 자유게시판과 자료게시판은 동아리원 |
| 작성자 이메일, 역할 | 넣지 않음 | ([auth 5-1-9](../../auth/backend/5-1-QUALITY-SECURITY.md)) |
| 첨부파일 내용 | 다운로드 주소로만 | 동아리원 |

- 공지는 공개라서 작성자 이름이 외부 방문자에게도 보인다. 운영진은 공지를 쓰면 이름이 공개된다는 것을 안다고 본다. (미확인. PM에게 확인 필요)
- 탈퇴한 작성자는 이름이 지워져 `null`로 나간다.
- 첨부파일 안에 개인정보가 있을 수 있다. 서버는 내용을 보지 않으므로 올리는 사람이 책임진다. 자료게시판 화면에 개인정보를 올리지 말라는 안내를 두는 것을 프론트엔드 세트에 남긴다.
- 로그에는 사용자 ID, 글 ID, 첨부 ID만 남긴다. 제목, 본문, 원래 파일 이름, 객체 키, 서명한 주소는 남기지 않는다. 서명한 주소는 만료 전까지 그 자체로 접근 권한이기 때문이다. (CWE-532)
