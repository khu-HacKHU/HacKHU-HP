# 5-1 보안

본 문서는 공지 API의 인증 수준과 권한 규칙, 입력 검증, 개인정보와 위협 모델을 정한다. 공통 규칙은 시큐어 코딩 규칙을 따른다. ([secure-coding.md](../../../security/secure-coding.md)) 이번 판은 공지만 다룬다. 자유게시판과 자료게시판은 #31에서 덧붙인다.

<br>

### 5-1-1. 인증 수준

인증 수준의 정의는 인증권한 세트를 따른다. ([auth 5-1-1](../../auth/backend/5-1-QUALITY-SECURITY.md))

| 수준 | 통과하는 사람 |
|---|---|
| 공개 | 누구나 |
| 운영진 | 역할이 `STAFF` 이상 |
| 관리자 | 역할이 `ADMIN` |

- 승인 대기 회원(`PENDING`)은 방문자와 같다. 공지에서는 공개 API만 통과한다.
- 공지 목록과 상세는 Security 설정의 공개 목록에 `GET` 메서드로만 적는다. 같은 경로의 `POST`, `PUT`, `DELETE`는 공개 목록에 넣지 않는다.

<br>

### 5-1-2. API별 인증 수준과 권한 검사

API 경로는 계약 문서를 따른다. ([4-2-INTERACTION-CONTRACT.md](4-2-INTERACTION-CONTRACT.md))

| API | 인증 수준 | 추가 검사 |
|---|---|---|
| 공지 목록 | 공개 | |
| 공지 상세 | 공개 | 글의 `board_type`이 `NOTICE`인지 |
| 공지 작성 | 운영진 | |
| 공지 수정 | 운영진 | 글의 `board_type`이 `NOTICE`인지 <br> 5-1-3의 작성자 규칙 |
| 공지 삭제 | 운영진 | 글의 `board_type`이 `NOTICE`인지 <br> 5-1-3의 작성자 규칙 |

<br>

### 5-1-3. 권한 규칙

**공지 작성** (USER-STORIES.md 2절)

- 운영진과 관리자만 쓴다.
- 작성자는 access 토큰으로 정한 현재 사용자의 ID다. 요청 본문, 쿼리, 헤더에서 받지 않는다.

**공지 수정과 삭제** (USER-STORIES.md 1절, 2절)

아래 둘 중 하나를 만족하면 통과한다.

| 요청한 사람 | 통과 조건 |
|---|---|
| 관리자 (`ADMIN`) | 모든 공지 |
| 운영진 (`STAFF`) | 글의 `author_id`가 현재 사용자의 ID와 같음 |

- 작성자 확인은 현재 사용자 ID와 DB에서 읽은 `author_id`를 비교한다. 요청에 담긴 작성자 정보를 믿지 않는다. (CWE-639)
- 운영진에서 동아리원으로 내려간 사람은 자기가 쓴 공지도 고치거나 지울 수 없다. 공지 쓰기가 운영진의 권한이기 때문이다. 이 공지는 관리자가 관리한다. 근거는 사용자 스토리 1절 상황표의 "권한이 없는 사람은 다른 방법으로 시도해도 막힘"이다. (USER-STORIES.md 1절, [DECISIONS.md](DECISIONS.md) B4)
- 다른 운영진의 공지는 관리자만 고치고 지운다. (USER-STORIES.md 2절)

**검사 순서**

1. 인증 수준을 확인한다. 토큰이 없거나 무효면 401, 운영진이 아니면 403 `FORBIDDEN`.
2. `id`와 `board_type = 'NOTICE'`로 글을 읽는다. 없으면 404 `POST_NOT_FOUND`.
3. 작성자 규칙을 확인한다. 통과하지 못하면 403 `POST_FORBIDDEN`.

공지는 공개 리소스라서 남의 공지라는 이유로 404를 주어 존재를 숨기지 않는다. 다른 게시판 글은 2단계에서 공지가 아닌 것으로 걸러져 404가 된다.

<br>

### 5-1-4. 게시판 종류 구분

세 게시판이 `post` 테이블 하나를 같이 쓴다. ([3-2-DESIGN-DB-SCHEMA.md](3-2-DESIGN-DB-SCHEMA.md)) 그래서 공지 API가 다른 게시판의 글을 읽거나 바꾸지 않도록 아래를 지킨다.

- 공지 API의 모든 조회, 수정, 삭제 쿼리는 조건에 `board_type = 'NOTICE'`를 넣는다. `id`만으로 글을 읽은 뒤 애플리케이션에서 종류를 비교하지 않는다. 비교를 빠뜨리면 공개 API로 동아리원 전용 글이 열리기 때문이다.
- `board_type`은 요청에서 받지 않는다. 컨트롤러가 정한 값을 서비스에 넘긴다.
- 테스트에 "공지 API로 다른 게시판 글 ID를 부르면 404" 케이스를 둔다. 자유게시판이 생기는 #31부터 실제로 확인할 수 있다.

<br>

### 5-1-5. 입력 검증

- 요청 DTO는 `title`과 `content`만 가진다. `id`, `authorId`, `boardType`, `createdAt`, `updatedAt`이 없다. (CWE-915)
- `title`은 앞뒤 공백을 지운 뒤 길이를 검사한다. 제어 문자와 양방향 텍스트 제어 문자(U+202A~U+202E, U+2066~U+2069)를 거부한다. 제목은 목록에서 다른 글과 나란히 보이므로 글자 방향을 뒤집어 다른 글처럼 보이게 하는 것을 막는다.
- `content`는 줄바꿈(`\n`)과 탭을 뺀 제어 문자를 거부한다. 특히 NUL(U+0000)은 PostgreSQL `TEXT`에 저장할 수 없어서 검사하지 않으면 500이 난다.
- 길이는 코드 포인트 단위로 센다. (3-2-DESIGN-DB-SCHEMA.md 3-2-2)
- 길이 검사를 통과하지 못하면 400 `INVALID_INPUT`과 필드별 사유를 준다. 사유에 입력값을 다시 넣지 않는다.
- 요청 본문 전체 크기는 64KB까지 받는다. 본문 10,000자가 UTF-8로 최대 40KB이므로 정상 요청은 넉넉히 들어간다. 큰 본문을 보내 서버 메모리를 쓰게 하는 것을 막는다.
  - Spring MVC와 Tomcat에는 JSON 본문 크기를 막는 기본 설정이 없다. `server.tomcat.max-http-form-post-size`는 폼 요청에만 적용된다. 그래서 직접 건다.
  - `Content-Length`만 보면 `Transfer-Encoding: chunked` 요청이 빠져나간다. 읽은 바이트를 세다가 넘으면 끊는 방식이어야 한다.
  - 거는 방법(필터 위치, 공지에만 걸지 전역으로 걸지)은 첫 쓰기 API인 #32에서 정한다. 전역으로 걸면 다른 팀 API에도 영향이 있어 PL과 정한다.
- 경로의 `noticeId`와 쿼리의 `page`, `size`는 정수만 받는다. `size`는 20을 넘으면 20으로 맞춘다.
  - 전역 설정(`spring.data.web.pageable.max-page-size: 100`)은 100으로 자르므로 20 상한은 걸리지 않는다. `Pageable`을 그대로 쓰지 않고 서비스가 `Math.min(size, 20)`으로 직접 맞춘다.
- `sort`는 허용 목록(`createdAt,desc` 하나)으로 먼저 검사하고, 맞지 않으면 쿼리를 실행하기 전에 400으로 거부한다. 받은 값을 쿼리에 넘기지 않고 서버가 고정한 정렬만 건다. 없는 필드를 그대로 넘기면 500과 ERROR 로그가 생기기 때문이다. (CWE-89)

<br>

### 5-1-6. 출력과 XSS

- 서버는 제목과 본문을 받은 글자 그대로 저장하고 JSON으로 준다. HTML 이스케이프나 태그 제거를 저장할 때 하지 않는다. 저장 단계에서 바꾸면 다른 화면에서 두 번 이스케이프되거나, 거르는 규칙을 우회하는 입력이 생기기 때문이다.
- XSS는 출력 단계에서 막는다. 프론트엔드는 제목과 본문을 글자로 출력하고 HTML로 해석하지 않는다. (CWE-79, [secure-coding.md](../../../security/secure-coding.md) 4절)
- 응답은 `Content-Type: application/json`이다. 브라우저가 공지 응답을 HTML로 해석하지 않는다.

<br>

### 5-1-7. 개인정보

| 정보 | 응답에 넣는 곳 | 이유 |
|---|---|---|
| 작성자 ID | 목록, 상세 | 프론트엔드가 수정과 삭제 버튼을 보일지 정함 |
| 작성자 이름 | 목록, 상세 | 누가 쓴 공지인지 보여 줌 |
| 작성자 이메일, 역할 | 넣지 않음 | 공지에 필요 없음 ([auth 5-1-9](../../auth/backend/5-1-QUALITY-SECURITY.md)) |

- 공지는 공개라서 작성자 이름이 외부 방문자에게도 보인다. 운영진은 공지를 쓰면 이름이 공개된다는 것을 안다고 본다. (미확인. PM에게 확인 필요)
- 탈퇴한 작성자는 이름이 지워져 `null`로 나간다.
- 로그에는 사용자 ID와 글 ID만 남긴다. 제목과 본문은 남기지 않는다. (CWE-532)

### 5-1-8. 기록

아래 사건을 로그로 남긴다. 로그 형식과 보존은 관측 문서에서 정한다. ([5-4-QUALITY-OBSERVABILITY.md](5-4-QUALITY-OBSERVABILITY.md))

| 사건 | 남기는 것 |
|---|---|
| 관리자가 남의 공지를 고치거나 지움 | 처리한 사람 ID, 글 ID, 원래 작성자 ID, 동작(수정, 삭제) |
| 권한 거부(403) | 사용자 ID, 요청 경로 <br> 인증권한 세트의 공통 처리가 남김 |

관리자 작업 기록은 시큐어 코딩 규칙 1절을 따른다.

| 위협 | 노리는 곳 | 대응 | 남는 위험 |
|---|---|---|---|
| 동아리원이나 승인 대기 회원이 공지를 씀 | 공지 작성 | 운영진 수준 검사, 역할은 요청마다 DB에서 읽음 | |
| 화면을 거치지 않고 API를 직접 불러 권한 우회 | 공지 작성, 수정, 삭제 | 모든 쓰기 API에서 서버가 역할과 작성자를 검사함 | |

| 요청 본문에 `authorId`를 넣어 남의 이름으로 공지를 씀 | 공지 작성, 수정 | DTO에 `authorId` 없음, 작성자는 토큰의 사용자 (CWE-915) | |
| 요청 본문에 `boardType`을 넣어 다른 게시판에 글을 씀 | 공지 작성, 수정 | DTO에 `boardType` 없음, 컨트롤러가 값을 정함 | |
| 공지 API에 다른 게시판 글 ID를 넣어 동아리원 전용 글을 읽거나 바꿈 | 공지 상세, 수정, 삭제 | 모든 쿼리에 `board_type = 'NOTICE'` 조건, 테스트로 확인 (5-1-4) | 쿼리 하나라도 조건을 빠뜨리면 열림 <br> 리뷰와 테스트로만 막음 |
| 순차 ID로 글을 하나씩 열람 | 공지 상세 | 공지는 공개라서 숨길 대상이 아님 <br> 다른 게시판 글은 404로 존재를 숨김 | 지운 공지와 다른 게시판 글의 ID 사이 간격으로 전체 글 수를 짐작할 수 있음 <br> 받아들임 |
| 저장형 XSS | 공지 상세, 목록, 메인 화면 | 프론트엔드가 글자로 출력, HTML 해석 금지, CSP (CWE-79) | 프론트엔드 한 곳이라도 HTML로 출력하면 공지를 보는 모든 사람이 영향받음 <br> 공개 화면이라 영향이 큼 |
| 양방향 제어 문자로 제목을 위장 | 공지 목록 | 제목에서 거부 | 본문에서는 거부하지 않음 |
| NUL 문자로 서버 오류 유발 | 공지 작성, 수정 | 제어 문자 거부 | |
| 큰 본문으로 메모리와 저장 공간 소모 | 공지 작성, 수정 | 요청 크기 64KB 제한, 본문 10,000자 제한, 운영진만 씀 | |
| 공개 목록과 상세에 대량 요청 | 공지 목록, 상세 | 페이지 크기 최대 20 | 요청 횟수 제한이 없음 <br> 필요해지면 배포 문서에서 WAF를 둠 |
| 강등된 운영진이 예전 토큰으로 계속 공지를 씀 | 공지 작성, 수정, 삭제 | 인증권한 세트가 요청마다 DB에서 역할을 읽음 (CWE-613) | |

| 관리자가 남의 공지를 몰래 고침 | 공지 수정, 삭제 | 관리자 작업 로그 | 공지 화면에서는 누가 고쳤는지 보이지 않음 |
| CSRF로 공지를 쓰거나 지움 | 공지 작성, 수정, 삭제 | access 토큰을 헤더로만 받음, 쿠키로 인증하지 않음, JSON만 받음 | |
