# 게시판 백엔드 결정 기록

결정 시점의 기록이다. 쓴 뒤 고치지 않고, 결정이 바뀌면 새 줄을 덧붙이고 옛 줄의 상태만 바꾼다.

| 결정 | 날짜 | 상태 | 배경 | 채택 | 대안 | 영향 |
|---|---|---|---|---|---|---|
| B1. 세 게시판이 `post` 테이블 하나를 같이 쓴다 | 2026-11-07 | 채택 | 공지, 자유게시판, 자료게시판의 글이 모두 제목, 본문, 작성자, 작성 시각으로 이루어진다(USER-STORIES.md 1절). #29가 테이블을 하나로 할지 정해 달라고 했다. | `post` 테이블 하나에 `board_type` 컬럼으로 게시판을 구분한다. 첨부파일은 자료게시판 글에만 붙으므로 #31에서 별도 테이블로 둔다. | 게시판마다 테이블을 두는 안. 같은 컬럼과 같은 코드를 세 번 만들게 되고, 메인 화면처럼 여러 게시판을 함께 보는 곳이 생기면 합쳐 읽기 어렵다. 대신 쿼리에서 게시판 조건을 빠뜨려도 다른 게시판 글이 섞이지 않는 장점은 잃는다. | 모든 쿼리에 `board_type` 조건이 필요하다. 빠뜨리면 공개 API로 동아리원 전용 글이 열리므로 5-1-4의 규칙과 테스트로 막는다. |
| B2. 게시판마다 API 경로를 따로 둔다 | 2026-11-07 | 채택 | 공지는 조회가 공개이고 자유게시판과 자료게시판은 동아리원 전용이다(D7). | 공지는 `/api/v1/notices`를 쓴다. 자유게시판과 자료게시판 경로는 #31에서 정한다. | `/api/v1/boards/{boardType}/posts`처럼 게시판 종류를 경로 변수로 받는 안. 같은 경로 패턴에서 공개 여부가 경로 변수 값에 따라 달라져 Security 설정의 공개 목록으로 표현하기 어렵고, 값 검사를 빠뜨리면 비공개 게시판이 열린다. | 게시판마다 컨트롤러가 생긴다. 서비스와 저장소는 함께 쓰고 컨트롤러가 `board_type`을 정해 넘긴다. |
| B3. 지운 글은 행을 바로 지운다 | 2026-11-07 | 채택 | 사용자 스토리에 지운 글을 복구하거나 보관하라는 요구가 없다. | 삭제 API가 행을 지운다. 복구 기능은 없다. | 삭제 시각 컬럼을 두고 숨기는 안. 모든 조회 쿼리에 삭제 조건을 더해야 해서 `board_type` 조건과 함께 빠뜨리기 쉬운 조건이 둘이 된다. 관리자가 지운 공지를 되살려야 하는 요구가 생기면 다시 검토한다. | 잘못 지운 글은 되살릴 수 없다. 관리자가 남의 글을 지운 기록은 로그로만 남는다(5-1-8). 자료게시판 첨부파일의 S3 객체를 함께 지우는 방법은 #31에서 정한다. |
| B4. 공지를 고치고 지우려면 작성 당시가 아니라 지금 운영진이어야 한다 | 2026-11-07 | 채택 | 사용자 스토리는 공지의 수정과 삭제를 "작성자와 관리자"로 정했다(USER-STORIES.md 1절). 운영진이 동아리원으로 내려간 뒤에도 자기 공지를 고칠 수 있는지는 정하지 않았다. | 공지 수정과 삭제는 운영진 수준을 먼저 확인하고, 그다음 작성자인지 확인한다. 관리자는 모든 공지를 고치고 지운다. | 작성자이기만 하면 역할과 상관없이 허용하는 안. 운영을 그만둔 사람이 동아리 이름으로 나가는 공지를 계속 바꿀 수 있다. | 강등된 사람의 공지는 관리자가 관리한다. 사용자 스토리와 해석이 다를 수 있어 PM 확인이 필요하다. |
