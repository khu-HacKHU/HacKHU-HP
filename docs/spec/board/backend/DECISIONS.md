# 게시판 백엔드 결정 기록

결정 시점의 기록이다. 쓴 뒤 고치지 않고, 결정이 바뀌면 새 줄을 덧붙이고 옛 줄의 상태만 바꾼다.

| 결정 | 날짜 | 상태 | 배경 | 채택 | 대안 | 영향 |
|---|---|---|---|---|---|---|
| B1. 세 게시판이 `post` 테이블 하나를 같이 쓴다 | 2026-11-07 | 채택 | 공지, 자유게시판, 자료게시판의 글이 모두 제목, 본문, 작성자, 작성 시각으로 이루어진다(USER-STORIES.md 1절). #29가 테이블을 하나로 할지 정해 달라고 했다. | `post` 테이블 하나에 `board_type` 컬럼으로 게시판을 구분한다. 첨부파일은 자료게시판 글에만 붙으므로 #31에서 별도 테이블로 둔다. | 게시판마다 테이블을 두는 안. 같은 컬럼과 같은 코드를 세 번 만들게 되고, 메인 화면처럼 여러 게시판을 함께 보는 곳이 생기면 합쳐 읽기 어렵다. 대신 쿼리에서 게시판 조건을 빠뜨려도 다른 게시판 글이 섞이지 않는 장점은 잃는다. | 모든 쿼리에 `board_type` 조건이 필요하다. 빠뜨리면 공개 API로 동아리원 전용 글이 열리므로 5-1-4의 규칙과 테스트로 막는다. |
| B2. 게시판마다 API 경로를 따로 둔다 | 2026-11-07 | 채택 | 공지는 조회가 공개이고 자유게시판과 자료게시판은 동아리원 전용이다(D7). | 공지는 `/api/v1/notices`를 쓴다. 자유게시판과 자료게시판 경로는 #31에서 정한다. | `/api/v1/boards/{boardType}/posts`처럼 게시판 종류를 경로 변수로 받는 안. 같은 경로 패턴에서 공개 여부가 경로 변수 값에 따라 달라져 Security 설정의 공개 목록으로 표현하기 어렵고, 값 검사를 빠뜨리면 비공개 게시판이 열린다. | 게시판마다 컨트롤러가 생긴다. 서비스와 저장소는 함께 쓰고 컨트롤러가 `board_type`을 정해 넘긴다. |
| B3. 지운 글은 행을 바로 지운다 | 2026-11-07 | 채택 | 사용자 스토리에 지운 글을 복구하거나 보관하라는 요구가 없다. | 삭제 API가 행을 지운다. 복구 기능은 없다. | 삭제 시각 컬럼을 두고 숨기는 안. 모든 조회 쿼리에 삭제 조건을 더해야 해서 `board_type` 조건과 함께 빠뜨리기 쉬운 조건이 둘이 된다. 관리자가 지운 공지를 되살려야 하는 요구가 생기면 다시 검토한다. | 잘못 지운 글은 되살릴 수 없다. 관리자가 남의 글을 지운 기록은 로그로만 남는다(5-1-12). 자료게시판 첨부파일의 S3 객체를 함께 지우는 방법은 #31에서 정한다. |
| B4. 공지를 고치고 지우려면 작성 당시가 아니라 지금 운영진이어야 한다 | 2026-11-07 | 채택 | 사용자 스토리는 공지의 수정과 삭제를 "작성자와 관리자"로 정했다(USER-STORIES.md 1절). 운영진이 동아리원으로 내려간 뒤에도 자기 공지를 고칠 수 있는지는 정하지 않았다. | 공지 수정과 삭제는 운영진 수준을 먼저 확인하고, 그다음 작성자인지 확인한다. 관리자는 모든 공지를 고치고 지운다. | 작성자이기만 하면 역할과 상관없이 허용하는 안. 운영을 그만둔 사람이 동아리 이름으로 나가는 공지를 계속 바꿀 수 있다. | 강등된 사람의 공지는 관리자가 관리한다. 근거는 사용자 스토리 1절 상황표의 "권한이 없는 사람이 게시판을 봄 → 주소를 직접 입력하는 등 다른 방법으로 시도해도 막힘"이다. 동아리원으로 내려간 사람은 공지에 대한 권한이 없는 사람이다. 2절의 "운영진이 다른 사람의 공지를 고치려 함"도 지금 역할을 기준으로 읽는다(PR #110 리뷰). |
| B5. 자유게시판은 `/api/v1/free-posts`, 자료게시판은 `/api/v1/archive-posts`를 쓴다 | 2026-11-07 | 채택 | B2에서 게시판마다 경로를 나누기로 했고, 두 게시판 경로는 #31에서 정하기로 했다. | 자유게시판 `/api/v1/free-posts`, 자료게시판 `/api/v1/archive-posts`. 첨부는 자료게시판 글 아래(`/api/v1/archive-posts/{postId}/attachments/...`)에 둔다. | `/api/v1/boards/free`처럼 단수 명사나 게시판 이름을 경로에 쓰는 안. API 규약의 "kebab-case 복수형 명사"에 맞지 않는다. `/api/v1/resources`처럼 자료를 따로 부르는 안. 글이라는 공통점이 경로에서 사라진다. | 첨부는 항상 글을 거쳐 찾으므로 다른 글의 첨부 ID로 접근하는 것을 경로 구조로도 막는다(5-1-4). |
| B6. 다운로드 주소는 상세 응답에 넣지 않고 받을 때 따로 발급한다 | 2026-11-07 | 채택 | 다운로드 링크는 받은 지 10분이 지나면 열리지 않아야 한다(USER-STORIES.md 4절). 상세에 주소를 넣으면 상세를 볼 때마다 유효한 주소가 생긴다. | `POST /api/v1/archive-posts/{postId}/attachments/{attachmentId}/download-url`로 받기를 누를 때만 발급한다. | 상세 응답에 첨부마다 다운로드 주소를 넣는 안. 화면 하나로 받을 수 있어 간단하지만, 화면 캐시와 브라우저 기록에 유효한 주소가 남고 상세를 볼 때마다 서명한다. `GET`으로 발급하는 안. 주소가 브라우저 기록과 프록시 로그에 남기 쉽다. | 받기를 누르면 요청이 한 번 더 생긴다. 발급마다 로그가 남아 누가 무엇을 받았는지 알 수 있다. |
| B7. 동아리원 전용 게시판은 글을 찾기 전에 역할로 막는다 | 2026-11-07 | 채택 | 동아리원이 아닌 사람이 글 주소를 직접 열어도 내용이 보이면 안 된다(USER-STORIES.md 3절). 글이 있는지 없는지도 알려 주지 않는 것이 낫다. | 자유게시판, 자료게시판의 모든 API는 먼저 동아리원 수준을 확인한다. 방문자는 401, 승인 대기 회원은 403이고, 글 ID가 있든 없든 같다. 동아리원이 남의 글을 고치려 하면 404가 아니라 403을 준다. | 글을 먼저 찾고 권한을 보는 안. 없는 글은 404, 있는 글은 403이 되어 방문자가 글 ID를 넣어 보며 글이 있는지 알 수 있다. 남의 글 수정에도 404를 주는 안. 동아리원은 그 글을 볼 수 있으므로 숨길 이유가 없고 프론트엔드가 원인을 구분하기 어렵다. | Security 설정의 기본값(동아리원 이상)만으로 1단계가 걸린다. 승인 대기 안내와 권한 없음 안내는 응답 코드가 같아 프론트엔드가 내 역할로 나눈다. |
| B8. 첨부의 S3 객체는 커밋 뒤 같은 요청에서 지우고, 실패하면 경고 로그만 남긴다 | 2026-11-07 | 채택 | 글을 지우거나 글 수정에서 첨부를 빼면 S3 파일도 지워야 한다. B3에서 방법을 #31로 미뤘다. | DB 트랜잭션이 커밋된 뒤 같은 요청 안에서 S3 객체를 지운다. 삭제가 실패해도 응답은 성공으로 주고 객체 키와 함께 경고 로그를 남긴다. | 커밋 전에 지우는 안. 롤백되면 DB 행은 남고 파일만 사라진다. 삭제 대기 테이블과 재시도 작업을 두는 안. 확실하지만 테이블과 배치가 하나씩 늘어 MVP에 비해 크다. 갤러리도 같은 요청에서 바로 지운다. | 삭제 실패 시 파일이 S3에 남는다. DB에 없어 다운로드 주소는 발급되지 않는다. 경고 로그가 쌓이면 재시도 작업을 다시 검토한다. |
| B9. 첨부 형식은 파일 앞부분까지만 확인하고 zip 안의 구조는 확인하지 않는다 | 2026-11-07 | 채택 | docx, pptx, xlsx는 안쪽이 zip이라 앞부분만으로는 확장자만 바꾼 zip과 구분할 수 없다. 구조를 확인할지, 내려받기로만 제공하고 남는 위험을 받아들일지는 게시판팀이 정하기로 했다(D8). | 확정할 때 S3에서 앞 8바이트를 읽어 pdf는 `%PDF-`, 나머지는 `PK\x03\x04`인지만 확인한다. 다운로드는 항상 `attachment`로 내리고 형식을 고정한다. 동아리원만 올리고 받으며 올린 사람을 기록한다. | 서버가 파일 전체를 내려받아 압축을 풀고 `[Content_Types].xml`과 형식별 필수 파일을 확인하는 안. 확장자만 바꾼 zip은 막지만 파일 하나에 최대 20MB를 서버로 다시 가져와야 하고, 압축 폭탄 대응과 zip 파서의 취약점 관리가 새로 필요하다. | 동아리원이 문서인 척한 zip을 올리면 다른 동아리원이 받아서 직접 열 수 있다. 받은 사람이 직접 실행해야 피해가 생기므로 받아들인다. 운영 중에 악용되면 구조 확인을 다시 검토한다. |
| B10. 자료게시판 글을 고칠 때 첨부를 남기고, 빼고, 더할 수 있다 | 2026-11-07 | 채택 | 사용자 스토리는 글 수정은 정했지만 첨부를 바꿀 수 있는지는 정하지 않았다. 오타 난 자료를 바꾸려고 글을 지우고 다시 쓰면 작성 시각과 링크가 바뀐다. | 수정 요청에 남길 기존 첨부 ID(`attachmentIds`)와 새 업로드(`uploadIds`)를 함께 받는다. 빠진 기존 첨부는 지우고, 합쳐서 5개를 넘으면 거부한다. | 첨부는 작성할 때만 붙이고 수정에서는 제목과 본문만 바꾸는 안. 단순하지만 파일 하나를 바꾸려고 글을 지우고 다시 써야 한다. 첨부를 따로 더하고 지우는 API를 두는 안. 요청이 나뉘어 중간에 실패하면 첨부만 바뀐 상태가 남는다. | 수정 요청이 글과 첨부를 한 트랜잭션에서 바꾼다. 남길 첨부가 이 글의 것인지와 개수를 글 행을 잠근 뒤 확인해야 한다(5-1-8). 프론트엔드는 바꾸지 않을 때도 기존 첨부 ID를 모두 보낸다. |
