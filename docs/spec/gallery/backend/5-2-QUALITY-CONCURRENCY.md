# 5-2 동시성

본 문서는 갤러리 백엔드의 동시 요청, 중복 처리, 잠금과 순서 보장을 정한다.

<br>

### 5-2-1 조회 주소 서명 비용

앨범 목록과 상세는 사진마다 CloudFront 서명을 한 번씩 계산한다. 서명은 서버 안의 RSA 연산이라 외부 호출은 없지만, 목록 `size`가 최대 100이라 한 요청에 서명이 100번까지 늘 수 있다.

| 항목 | 값 |
|---|---|
| 서명 한 번 | RSA-2048 기준 1~2ms 정도 |
| 한 요청의 최대 서명 수 | 100 (목록 `size` 상한) |
| 지금 쓰는 크기 | 갤러리 목록 20, 메인 화면 4 |

지금은 캐시를 두지 않는다. 느려지면 `CloudFrontPhotoUrlResolver`에서 객체 키와 만료 구간을 키로 서명 결과를 캐시한다. 만료가 1시간이라 캐시가 잘 맞는 구조다.

<br>

### 5-2-2 앨범 삭제의 처리 순서

앨범 삭제는 DB와 S3 두 곳을 지운다. 둘을 한 번에 묶을 수 없어서, 실패했을 때 어느 쪽이 남는지를 순서로 정한다.

1. 앨범을 읽고 권한을 검사한다.
2. 사진의 객체 키를 읽어 둔다.
3. 앨범 행을 조건부로 지우고(`delete ... where id = ?`) 지운 행 수를 본다. 사진 행은 ON DELETE CASCADE로 같이 지워진다. DB 쪽 실패는 여기서 드러난다. 0행이면 404로 끝낸다.
4. S3 객체를 지운다.
5. 커밋한다.

| 실패 지점 | 결과 | 사용자 |
|---|---|---|
| 3 | 롤백, 아무것도 안 지워짐 | 다시 지우면 됨 |
| 4 | 예외로 롤백, 앨범 행은 남음 <br> S3 객체는 일부 지워졌을 수 있음 <br> **사진 일부가 깨진 앨범이 공개 목록에 남음** | 작성자나 관리자가 다시 지우면 정리됨. S3 삭제는 없는 키에도 성공해서 재시도가 안전함 |
| 5 | 드묾. S3는 지워졌는데 행이 남음 | 사진이 깨져 보임. 다시 지우면 정리됨 |

반대 순서(DB 커밋 뒤 S3 삭제)는 쓰지 않는다. S3가 실패하면 화면에서는 사라졌는데 받아 둔 사진 주소가 계속 열려서, "지운 앨범의 사진은 주소로도 볼 수 없음"(USER-STORIES 3절)을 어긴다. 대신 S3 호출 동안(사진 최대 20장) 트랜잭션을 잡고 있는데, 동아리 규모에서는 문제가 되지 않는다.

같은 앨범을 동시에 두 번 지우면(삭제 버튼을 빠르게 두 번 누르는 경우 등) 늦은 쪽은 404를 받는다. 두 요청이 모두 조회와 권한 검사를 통과할 수 있는데, 늦은 요청은 3에서 앞 요청의 행 잠금을 기다렸다가 앞 요청이 커밋하면 0행을 지운다. 그래서 엔티티 삭제(`delete(entity)`)가 아니라 조건부 삭제로 지운 행 수를 본다. 엔티티 삭제는 이 경우 낙관적 잠금 예외를 던져 500과 ERROR 로그가 된다 (CWE-779). 따로 잠그지 않는다.
