# 2 요구사항

본 문서는 프론트엔드가 갤러리 백엔드에 기대하는 제약을 측정 가능한 값으로 정한다.

<br>

### 1. 응답 시간

| API | 목표 (p95) |
|---|---|
| 앨범 목록 | 300ms 이하 |
| 앨범 상세 | 300ms 이하 |
| 업로드 주소 발급 | 500ms 이하 (S3 presigned 생성은 로컬 연산이라 외부 호출 없음) |
| 앨범 올리기 | 500ms 이하 (업로드 기록 조회 + 매직바이트 재검증을 API 안에서 전부 동기로 처리, 5-1 참고) |

동아리 내부 규모(동시 접속 수십 명)를 가정한다. 별도 성능 테스트는 두지 않는다.

<br>

### 2. 처리량

동시 사용자 수가 적어 처리량 목표를 따로 두지 않는다. 업로드 주소 발급 API는 **rate limit을 건다**. S4 Exploit 라운드에서 노려질 전형적인 리소스 소모 공격이라 판단해서다. **사용자 ID당 분당 5회 호출 + 시간당 발급 파일 수 100장**으로 이중 제한 (5-1 참고).

<br>

### 3. 보존 기간과 데이터 수명

| 데이터 | 수명 |
|---|---|
| 앨범·사진 메타데이터 | 삭제 전까지 무기한 |
| 사진 원본 (S3) | 앨범 삭제 요청과 **동기로 즉시 삭제**. 그레이스 기간은 CDN 캐시 TTL로 자연히 발생 (3-2, 5-1 참고) |
| 발급된 업로드 주소 | **10분** |
| 발급된 조회 주소 | **CDN 주소라 서버가 만료시간을 관리하지 않음.** 그레이스는 캐시 TTL 10분으로 구현한다(USER-STORIES 3절). 실제 설정은 인프라팀이 CloudFront에 건다 |

<br>

### 4. 가용성

별도 SLA를 두지 않는다. S3 장애 시 업로드만 막히고 조회(이미 저장된 메타데이터)는 DB만으로 가능해야 한다.
