# 5-1 보안

공통 규칙은 [docs/security/secure-coding.md](../../../security/secure-coding.md)를 따른다. 여기는 갤러리에만 해당하는 내용만 적는다.

<br>

### 1. API별 인증 수준과 권한

| API | 인증 수준 | 권한 검사 |
|---|---|---|
| 앨범 목록·상세 조회 | 공개 | 없음 |
| 업로드 주소 발급 | 필요 | 동아리원 이상 (승인 대기 회원·방문자 거부) |
| 앨범 올리기 | 필요 | 동아리원 이상 |
| 앨범 삭제 (#59) | 필요 | 작성자 본인 또는 관리자 |

현재 사용자·역할 확인은 #22(인증권한팀)가 제공하는 방법을 쓴다. 이 이슈가 끝나기 전에는 구현에 들어갈 수 없다.

<br>

### 2. 입력 검증

- `title`: 1~100자, 빈 문자열 금지.
- `eventDate`: ISO 8601 날짜. **업로드 시점 기준 오늘까지만 허용, 미래 날짜 금지**. 앨범은 이미 일어난 행사의 사진이라 미래 날짜는 데이터 정합성 위반이다.
- `files`/`photoKeys` 개수: 1~20개, 서버가 강제 (DB가 아니라 서비스 레이어).
- `contentType`: jpg/png/webp의 MIME 화이트리스트만 허용.
- 파일 크기: 업로드 주소 발급 요청에 `size`를 받는다. **발급 시점에 10MB를 넘으면 그 자리에서 400으로 거부한다.** 통과한 `size`는 presigned PUT 서명에 정확한 `Content-Length`로 포함시킨다. 실제 업로드 바이트 수가 그 값과 다르면 S3가 서명 불일치로 업로드 자체를 거부하므로, 신고한 크기보다 큰 파일은 올라갈 수 없다. (PUT은 `content-length-range` 같은 범위 조건은 못 걸지만, 정확한 값 하나는 서명에 넣을 수 있다.)

<br>

### 3. 개인정보

앨범·사진 테이블 자체에는 개인정보가 없다. `uploader_id`로 사용자 테이블을 참조하는 정도. 탈퇴 시 사용자 테이블에서 이름·이메일을 지우는 처리는 인증권한팀 책임이고 여기서는 FK만 그대로 둔다.

<br>

### 4. 위협 모델링

| 위협 | 대응 |
|---|---|
| Mass Assignment (요청 DTO로 `uploaderId`, `role` 주입) | 해당 필드를 DTO에 두지 않는다. 현재 사용자는 인증 토큰에서만 꺼낸다 |
| 파일 형식 위장 (Content-Type 헤더 위조, CWE-434) | presigned PUT 서명에 Content-Type을 고정해서 1차로 막지만, 실제 바이트 내용까지는 확인 못 함. **앨범 생성 확정 단계에서 서버가 S3 Range GetObject(첫 12바이트)로 매직바이트를 동기 재검증한다(필수)** (secure-coding.md 5절) |
| 남의 업로드 키 재사용 (공개 CDN URL에서 object_key 추측·열람 가능) | 클라이언트가 object_key를 직접 다루지 않는다. 발급 시 `uploadId`만 내려주고, 서버가 `global/storage`의 발급 기록 테이블(`uploadId`→`user_id`, `status`, `expires_at`)로 소유자·만료·사용 여부를 확인한다 |
| 객체 키 추측으로 직접 접근 | 키는 UUID 기반으로 서버가 생성, 추측 불가. S3 버킷은 퍼블릭 액세스 완전 차단 |
| 업로드 주소 남발 (스토리지 비용 공격) | **rate limit**: 사용자 ID당 **분당 5회 호출 + 시간당 발급 파일 수 100장**으로 이중 제한, 초과 시 429. in-memory 카운터로 처리(인스턴스 하나뿐, D3) |
| 삭제 후 잔존 조회 주소 | USER-STORIES: 삭제 후 10분 지나면 열리지 않아야 함. **S3 객체는 요청과 동기로 즉시 삭제, CDN 캐시 TTL 10분이 그레이스 기간을 그대로 제공**. 실제 설정은 인프라팀이 CloudFront에 건다 |
| IDOR (다른 사람 앨범 삭제) | 삭제 API에서 `uploader_id` 또는 관리자 역할 확인. 조회는 전부 공개라 해당 없음 |
| 확정 안 하고 방치된 업로드가 쌓임 (10MB 이하라도 사용자당 시간당 최대 100장, 1GB까지 누적 가능) | 발급 요청에 `size`를 받아 10MB 초과면 발급 자체를 거부하고, 통과한 크기는 presigned PUT 서명의 정확한 `Content-Length`로 고정해서 신고보다 큰 업로드는 S3가 거부한다. 그래도 10MB 이하 파일이 확정 없이 쌓이는 건 이걸로 못 막으므로, 만료된 `ISSUED` 기록을 찾아 해당 S3 객체를 지우는 배치를 둔다 (`global/storage`, PL 소유) |

<br>

### 5. 로그

관리자의 앨범 삭제(타인 소유)는 누가 무엇을 지웠는지 로그로 남긴다 (secure-coding.md 1절).
