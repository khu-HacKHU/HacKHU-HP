# DECISIONS.md

본 문서는 제품 단위 결정과 PM 결정의 이유와 이력을 기록한다.

현재 적용 기준은 각 명세에 있고, 여기에는 결정 당시의 배경과 버린 대안을 남긴다. 팀의 기술 결정은 각 세트의 `DECISIONS.md`에 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다.
- 쓴 뒤 고치지 않는다. 결정이 바뀌면 새 결정을 덧붙이고 이전 결정의 상태를 "대체됨 (D번호)"로 바꾼다.
- 날짜순으로 아래에 쌓는다.

<br>

### 2. 결정

**D1. 백엔드를 Spring Boot로 만든다**

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 날짜 | 2026-10-08 |
| 배경 | 기획 단계에서 Spring과 FastAPI가 후보였다. |
| 채택 | Spring Boot 4.1, Java 21, PostgreSQL 17. PL이 뼈대를 만들었다. (PR #2) |
| 대안 | FastAPI. 팀원의 진입 장벽은 낮지만 운영진이 리뷰하기 어렵다. 인증 담당 참가자가 Spring을 써 봤다. |
| 영향 | Python만 써 본 참가자는 Java와 Spring을 새로 익혀야 한다. |

**D2. 프론트엔드를 React로 만든다**

| 항목 | 내용 |

| 날짜 | 2026-10-08 |

**D3. 서비스를 나누지 않는다**

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 날짜 | 2026-10-11 |
| 배경 | 명세를 기능별로 나누면서 배포도 기능별로 나눌지 검토했다. |
| 채택 | 백엔드 하나, 프론트엔드 하나로 배포한다. 백엔드는 기능별 패키지로 경계를 나눈다. |
| 대안 | MSA. 참가자 10명 중 입문자가 4명이고 개발 기간이 약 5주라 서비스 간 인증, 호출 실패 처리, 서비스별 파이프라인과 DB를 감당하기 어렵다. 게시판과 갤러리가 모두 인증에 의존해 나눠도 이점이 없다. |
| 영향 | 배포 문서를 기능마다 두지 않고 하나로 둔다. ([DEPLOYMENT.md](DEPLOYMENT.md)) |

<br>

**D4. 이메일과 비밀번호로 가입하고 운영진이 승인한다**

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 날짜 | 2026-10-11 |
| 배경 | 동아리 홈페이지라서 가입한 사람이 바로 동아리원이 되면 안 된다. |
| 채택 | 이메일, 비밀번호, 이름으로 가입하면 승인 대기가 되고 운영진이 승인하면 동아리원이 된다. 거절하면 계정을 삭제한다. |
| 대안 | 학교 이메일 인증. 메일 발송 인프라(AWS SES, 도메인 인증)가 필요해 인프라팀의 일이 크게 는다. 참가자 상당수가 학교 메일이 아닌 메일을 쓴다. |
| 영향 | 승인 대기 상태와 승인 화면이 필요하다. 메일을 보내지 않으므로 비밀번호 재설정은 운영진이 임시 비밀번호를 발급하는 방식이다. |

| 영향 | S2 인증 일정에서 OAuth2 착수가 빠진다. |

**D6. 역할을 5단계로 둔다**

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 날짜 | 2026-10-11 |

| 채택 | 방문자, 승인 대기 회원, 동아리원, 운영진, 관리자. 역할 변경은 관리자만 한다. 처음 관리자는 PM과 PL이다. 마지막 관리자는 내릴 수 없다. |
| 대안 | 승인 대기 회원 없이 4단계. 승인을 기다리는 사람을 나타낼 수 없다. |
| 영향 | 모든 기능이 승인 대기 회원을 방문자와 같이 다룬다. ([PRODUCT.md](PRODUCT.md)) |

**D7. 공지와 갤러리는 공개하고 자유게시판과 자료게시판은 동아리원만 본다**

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 날짜 | 2026-10-11 |
| 배경 | 공지와 활동 사진은 외부에 알려야 하고, 자유게시판과 자료게시판은 동아리 내부 공간이다. |
| 채택 | 공지와 갤러리는 누구나 보고, 자유게시판과 자료게시판은 동아리원만 본다. 수정과 삭제는 작성자와 관리자만 한다. |
| 대안 | 모두 공개하거나 모두 회원 전용으로 하는 안. 공개와 비공개가 섞여 있어야 팀마다 남의 글이나 비공개 글을 막는 권한 검사(IDOR)를 직접 다뤄 볼 수 있다. |
| 영향 | 게시판팀은 같은 기능에서 공개와 비공개 권한 검사를 모두 구현한다. |

<br>

**D8. 업로드 파일의 형식과 크기를 제한한다**

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 날짜 | 2026-10-11 |
| 배경 | 갤러리 사진과 자료게시판 첨부가 파일 업로드를 쓴다. |
| 채택 | 갤러리는 jpg, png, webp, 10MB. 자료 첨부는 pdf, docx, pptx, xlsx, 20MB, 글 하나에 5개. SVG와 zip은 받지 않는다. |
| 대안 | 형식 제한 없이 받는 안. SVG는 안에 스크립트를 넣을 수 있고(XSS) zip은 안을 검사할 수 없다. |
| 영향 | 값은 각 기능의 사용자 스토리에 있다. docx, pptx, xlsx는 안쪽이 zip 구조라 파일 앞부분만 보고는 확장자만 바꾼 zip과 구분할 수 없다. 파일 구조를 확인할지, 내려받기로만 제공하고 남는 위험을 받아들일지는 게시판팀이 `board/backend/5-1-QUALITY-SECURITY.md`에서 정한다. 재검토 조건: 운영 중에 필요한 형식이나 크기가 생기면 바꾼다. |

**D9. 갤러리는 앨범 단위로 올린다**

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 날짜 | 2026-10-11 |
| 배경 | 활동 사진은 행사마다 여러 장이 생긴다. |
| 채택 | 앨범 하나에 제목, 활동 날짜와 사진 1장 이상 20장 이하. 수정하지 않고 지우고 다시 올린다. |
| 대안 | 사진 한 장 단위. 목록이 금방 어지러워진다. |
| 영향 | 갤러리팀의 테이블이 앨범과 사진 두 개가 된다. |

**D10. 메인 화면, 동아리 소개, 내 정보를 MVP에 넣는다**

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 날짜 | 2026-10-11 |
| 배경 | 명세 구조를 정하다가 어느 기능에도 속하지 않는 화면이 MVP 목록에 없다는 것이 드러났다. |
| 채택 | 메인 화면과 동아리 소개는 홈 기능으로 두고 게시판팀이 S3에 만든다. 내 정보(비밀번호 변경, 탈퇴)와 비밀번호 초기화는 인증권한 기능에 넣는다. |
| 대안 | 홈 기능을 PM이 직접 만드는 안. PM은 기능 개발을 하지 않는다는 원칙과 맞지 않는다. |
| 영향 | 게시판팀의 일이 늘어난다. 메인 화면은 다른 기능의 API를 쓰고 소개는 정적 화면이라 S3에 맞춘다. |

**D11. 명세를 기능 폴더와 백엔드, 프론트엔드 세트로 나눈다**

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 날짜 | 2026-10-11 |
| 배경 | 팀이 10/16까지 설계를 쓸 자리가 필요했다. |
| 채택 | `docs/spec/` 아래에 공통 문서와 기능 폴더를 둔다. 기능 폴더에는 PM이 쓰는 배경과 사용자 스토리, 팀이 쓰는 `backend/`와 `frontend/` 세트를 둔다. 세트는 박성준 멘토의 백엔드, 클라이언트 명세 구성을 따르고 번호는 세트 안에서만 쓴다. |
| 대안 | 하나의 층위 번호 체계로 모든 문서를 두는 안(LinKHU 방식). 프론트엔드만 있는 제품에 맞춘 구조라 기능과 백엔드, 프론트엔드가 섞인다. 멘토 원형의 도메인 계층과 작성 가이드 폴더는 규모에 비해 단계가 많아 뺐다. |
| 영향 | 배포와 디자인 시스템처럼 기능을 가로지르는 내용은 공통 문서로 올렸다. 세트의 설계 결정 문서는 두지 않고 `DECISIONS.md`의 상태로 현재 결정을 구분한다. 분석 이벤트를 쓰지 않아 이벤트 트래킹 문서도 두지 않는다. |
