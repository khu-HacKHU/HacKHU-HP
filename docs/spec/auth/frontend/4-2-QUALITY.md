# 4-2 품질

본 문서는 로그인 상태와 토큰을 어디에 어떻게 보관하는지, 인증 화면의 접근성 기준을 정한다. 다른 기능의 화면도 토큰 보관과 요청 공통 처리는 이 정의를 따른다.

백엔드가 주는 토큰의 형식과 실패 코드는 계약 문서에서 정한다. ([auth/backend/4-2-INTERACTION-CONTRACT.md](../backend/4-2-INTERACTION-CONTRACT.md) 4-2-1)

<br>

### 4-2-1. 토큰 보관 위치

| 토큰 | 보관 위치 | 수명 |
|---|---|---|
| access 토큰 | **브라우저 메모리.** 모듈 변수 하나에 둠 (`features/auth/session.ts`) | 15분. 새로고침하면 사라짐 |
| refresh 토큰 | 서버가 준 `HttpOnly` 쿠키. 프론트엔드 코드가 읽지 않음 | 14일 |

- access 토큰을 `localStorage`, `sessionStorage`, 쿠키, URL에 넣지 않는다. (CWE-922)
- access 토큰을 React 상태에 직접 두지 않고 모듈 변수에 둔다. 컴포넌트 밖의 요청 공통 처리(`lib/api.ts`)가 읽어야 하기 때문이다. 화면은 그 변수를 구독해서 다시 그린다.
- refresh 토큰은 `HttpOnly`라 JavaScript가 읽을 수 없다. 프론트엔드는 쿠키를 직접 다루지 않고 `credentials: 'include'`로 브라우저가 싣게만 한다.
- 토큰을 로그, 오류 메시지, 화면에 출력하지 않는다.

**왜 메모리인가**

`localStorage`에 두면 XSS 하나로 장기 토큰이 새어 나가고, 그 뒤로는 서버가 막을 방법이 없다. refresh 토큰을 `HttpOnly` 쿠키로 둔 이유가 그것인데, access 토큰을 `localStorage`에 두면 그 방어가 의미를 잃는다. 메모리에 두면 XSS가 토큰을 읽을 수는 있어도 **그 탭이 열려 있는 동안으로 한정**된다.

대신 새로고침마다 토큰이 사라지는 비용이 있다. 그것은 아래 복구로 해결한다.

<br>

### 4-2-2. 새로고침 뒤 로그인 상태 복구

1. 앱이 시작할 때 `POST /api/v1/auth/refresh`를 한 번 부른다.
2. 성공하면 응답의 `user`와 `accessToken`으로 로그인 상태를 세운다. 응답에 `user`가 함께 오므로 요청 한 번으로 끝난다. (4-2-5)
3. 실패하면(쿠키가 없거나 세션이 폐기됨) 로그인하지 않은 상태로 둔다. 오류를 화면에 보여 주지 않는다. 로그인하지 않은 방문자가 첫 화면을 열면 항상 이 경로를 지나기 때문이다.
4. 복구가 끝날 때까지 **로그인 여부를 단정하지 않는다.** 헤더는 그 사이 로그인 버튼도 사용자 이름도 보여 주지 않는다. 단정하면 로그인한 사용자가 새로고침할 때마다 로그인 버튼이 깜빡인다.

<br>

### 4-2-3. 요청 공통 처리

모든 API 요청은 `lib/api.ts`의 `request`를 지난다. 컴포넌트가 `fetch`를 직접 부르지 않는다. ([frontend/AGENTS.md](../../../../frontend/AGENTS.md))

- 모든 요청에 `credentials: 'include'`를 붙인다.
- 세션이 있으면 `Authorization: Bearer`를 붙인다. 쿼리스트링, 본문, 쿠키로 보내지 않는다.
- 본문이 있으면 `Content-Type: application/json`을 붙인다.
- `401`을 받으면 갱신을 한 번 시도하고 원래 요청을 **한 번만** 다시 보낸다. 다시 보낸 요청이 또 `401`이면 갱신을 다시 부르지 않고 로그인하지 않은 상태로 만든다.
- `/api/v1/auth/` 아래 경로의 `401`에는 갱신을 시도하지 않는다. 로그인 실패에 갱신을 시도하면 돌 수 있다.
- **갱신 요청은 한 번에 하나만 보낸다.** 여러 요청이 동시에 `401`을 받아도 갱신은 한 번만 부르고 결과를 같이 쓴다. 갱신은 refresh 토큰을 회전시키므로 동시에 부르면 뒤에 도착한 요청이 재사용으로 판정되어 세션이 끊긴다. (4-2-5)
- 시간 초과로 갱신 요청을 중간에 끊지 않는다. 끊은 요청의 응답이 늦게 도착해 쿠키가 뒤바뀌는 것을 막는다.

<br>

### 4-2-4. 갱신 결과가 다른 사용자일 때

갱신으로 받은 `user.id`가 원래 요청을 만든 사용자와 다르면 **원래 요청을 다시 보내지 않고 버린다.** (CWE-287)

refresh 쿠키는 브라우저의 모든 탭이 함께 쓴다. 다른 탭에서 다른 계정으로 로그인하면 쿠키가 그 계정의 것으로 덮어써지고, 갱신은 그 계정의 정상 토큰을 돌려준다. 그대로 다시 보내면 사용자 A가 쓴 글이 사용자 B 명의로 저장되거나 A의 화면에 B의 데이터가 보인다.

- 쓰기와 조회 요청 모두에 적용한다.
- 버린 뒤에는 탭의 현재 사용자를 갱신 결과의 사용자로 바꾸고 화면을 다시 그린다.
- 쓰던 입력은 지우지 않고 "다른 탭에서 계정이 바뀌어 요청을 보내지 않았다"고 안내한다.
- 이 확인은 서버가 대신할 수 없다. 갱신에 쓰인 refresh 토큰과 새로 발급한 access 토큰이 모두 B의 정상 토큰이기 때문이다.

<br>

### 4-2-5. 로그인 실패를 화면에 보여 주는 방식

서버는 이메일이 없는 것, 비밀번호가 틀린 것, 탈퇴한 계정을 모두 같은 `401 AUTH_INVALID_CREDENTIALS`로 준다. **화면도 나누지 않는다.**

- 안내 문구는 "이메일 또는 비밀번호가 올바르지 않습니다." 하나다.
- 어느 항목이 틀렸는지 표시하지 않는다. 나누어 보여 주면 그 이메일로 계정이 있는지 알려 주게 된다.
- 가입 화면의 `400`은 다르다. 서버가 `errors`에 항목별 사유를 주므로 그 입력창 아래에 보여 준다. 가입은 아직 계정이 없는 사람이 쓰는 화면이라 항목을 알려 줘도 계정 존재가 드러나지 않는다.
- `429`는 `Retry-After` 헤더의 초를 안내에 넣는다.

<br>

### 4-2-6. 접근성

UI 디자인 시스템의 기준을 따른다. ([UI-DESIGN-SYSTEM.md](../../UI-DESIGN-SYSTEM.md) 8절) 인증 화면에서 지키는 것은 아래와 같다.

- 모든 입력창에 화면에 보이는 `<label>`을 둔다. 안내 문구(placeholder)를 이름표 대신 쓰지 않는다.
- 오류 안내는 `role="alert"`로 두어 화면 낭독기가 바로 읽는다.
- 항목별 사유는 `aria-describedby`로 그 입력창과 잇고, 틀린 입력창에 `aria-invalid="true"`를 준다.
- 상태를 색으로만 알리지 않는다. 오류는 `coral` 테두리와 문구를 함께 쓴다.
- 키보드만으로 가입과 로그인을 끝낼 수 있다. 포커스를 받은 요소는 `lilac` 테두리로 보인다.
- `autocomplete`를 준다. 로그인은 `email`, `current-password`, 가입은 `email`, `name`, `new-password`다. 비밀번호 관리자가 올바른 칸을 채우게 하려는 것이다.

<br>

### 4-2-7. 아직 정하지 않은 것

- 성능 기준(첫 화면 표시 시간 등)은 정하지 않았다. 스테이징에 올린 뒤 측정해서 정한다.
- 비밀번호 변경 화면(#49, #51)의 흐름은 그 이슈에서 정한다. 임시 비밀번호로 로그인하면 `/password`로 보내는 것까지만 이 PR에서 했다.
