# 인증권한 백엔드 결정 기록

결정 시점의 기록이다. 쓴 뒤 고치지 않고, 결정이 바뀌면 새 줄을 덧붙이고 옛 줄의 상태만 바꾼다.

| 결정 | 날짜 | 상태 | 배경 | 채택 | 대안 | 영향 |
|---|---|---|---|---|---|---|
| A1. access 토큰(JWT)과 회전하는 refresh 토큰으로 인증한다 | 2026-11-05 | 채택 | 로그인 상태를 유지할 방법이 필요했다. 시큐어 코딩 규칙과 API 규약이 이미 JWT와 refresh 회전을 전제로 쓰여 있다. | access 토큰은 15분 JWT(HS256), refresh 토큰은 DB에 해시로 저장하는 무작위 값이고 쓸 때마다 회전한다. | 서버 세션 쿠키. 구현은 더 단순하지만 기존 문서를 고쳐야 하고, 보안 실습에서 토큰 검증과 재사용 감지를 다뤄 볼 기회가 없다. | `refresh_tokens` 테이블이 생긴다. 프론트엔드에 자동 갱신 흐름이 필요하다. |
| A2. 역할과 계정 상태는 요청마다 DB에서 읽는다 | 2026-11-05 | 채택 | 역할을 바꾸면 다시 로그인하지 않아도 바로 적용되어야 하고(USER-STORIES.md 4절), 탈퇴한 계정은 바로 막혀야 한다. | access 토큰에는 사용자 ID만 넣고, 인증할 때마다 기본 키로 계정을 읽어 역할, 탈퇴 여부, `tokens_valid_after`를 확인한다. | 역할을 토큰 클레임에 넣는 안. DB 조회는 줄지만 역할 변경과 탈퇴가 토큰 만료(15분)까지 반영되지 않는다. | 요청마다 PK 조회 1건이 더해진다(20ms 이하). |
| A3. refresh 토큰은 HttpOnly 쿠키에, access 토큰은 프론트엔드 메모리에 둔다 | 2026-11-05 | 채택 | 토큰 보관 위치에 따라 XSS와 CSRF 위험이 달라진다. | refresh 토큰은 `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api/v1/auth` 쿠키. access 토큰은 응답 본문으로 주고 프론트엔드가 메모리에만 둔다. | `localStorage`에 둘 다 두는 안은 XSS 한 번에 장기 토큰이 털린다. 둘 다 쿠키에 두는 안은 모든 API에 CSRF 대응이 필요하다. | 프론트엔드와 API가 같은 사이트여야 한다(배포 문서에서 확인). 프론트엔드 세트 4-2가 이 결정을 따른다. |
| A4. 로그인은 활동하는 동안 이어지고 최대 30일 유지한다 | 2026-11-05 | 채택 | access 토큰이 짧아도 쓰는 도중에 로그아웃되면 안 된다. 공용 PC에 로그인이 무기한 남는 것도 막아야 한다. | access 15분, refresh는 마지막 갱신부터 14일, 로그인 묶음은 로그인부터 최대 30일. 동시 갱신을 위해 직전 refresh 토큰을 10초 동안 받아 준다. | 최대 수명 없이 계속 연장하는 안. 공용 PC에서 위험하다. | 30일마다 다시 로그인한다. |
| A5. 승인 대기를 역할 값 `PENDING`으로 표현한다 | 2026-11-05 | 채택 | 승인 대기 회원은 역할 순서에서 방문자 바로 위에 있다(PRODUCT.md 4절). | `role`은 `PENDING`, `MEMBER`, `STAFF`, `ADMIN` 중 하나이고 순서로 비교한다. | 역할과 별도로 상태 컬럼을 두는 안. 권한을 판단할 때 두 컬럼을 함께 봐야 해서 검사를 빠뜨리기 쉽다. | 다른 팀은 역할 하나만 비교하면 된다. |
| A6. 회원 테이블 이름을 `users`로 한다 | 2026-11-05 | 채택 | `user`는 PostgreSQL 예약어라 매번 따옴표가 필요하다. | `users`. 다른 기능은 `users.id`를 참조한다. | `member`. 역할 이름(동아리원)과 헷갈린다. | 갤러리 설계(PR #89)의 `user.id` 참조를 `users.id`로 맞춘다. |
| A7. 탈퇴는 익명화하고 거절은 행을 지운다 | 2026-11-05 | 채택 | 탈퇴해도 글과 앨범은 남기고 작성자를 "탈퇴한 회원"으로 보여야 한다(USER-STORIES.md 5절). 거절하면 계정을 지우고 같은 이메일로 다시 가입할 수 있어야 한다(3절). | 탈퇴하면 이메일, 이름, 비밀번호 해시를 NULL로 바꾸고 `withdrawn_at`을 기록한다. 거절하면 행을 지운다. 이메일 유니크는 NULL이 아닌 행에만 건다. | 탈퇴도 행을 지우고 글의 작성자를 NULL로 바꾸는 안. 다른 팀의 외래 키 규칙이 모두 달라지고 작성자 권한 검사에서 NULL을 다뤄야 한다. | 탈퇴한 사람도 같은 이메일로 다시 가입할 수 있다. |
| A8. 비밀번호는 10자 이상 64자 이하이고 조합 규칙을 두지 않는다 | 2026-11-05 | 채택 | 비밀번호 규칙을 인증권한팀이 정하기로 했다(USER-STORIES.md 1절). | 10자 이상 64자 이하, UTF-8 72바이트 이하, 이메일과 같으면 거부. bcrypt cost 12. | 8자 이상에 영문, 숫자, 특수문자 조합을 강제하는 안. 조합 강제는 예측하기 쉬운 비밀번호를 늘린다(NIST SP 800-63B). | 프론트엔드 가입 화면의 안내 문구가 이 규칙을 따른다. |
| A9. 임시 비밀번호를 발급하면 기존 비밀번호를 바꾼다 | 2026-11-05 | 채택 | 운영진이 임시 비밀번호로 남의 계정에 들어가는 것을 줄여야 한다(USER-STORIES.md 6절). | 기존 비밀번호 해시를 임시 비밀번호 해시로 바꾸고 대상의 모든 로그인을 끊는다. 처음 로그인하면 사용으로 기록하고 비밀번호 변경 전에는 일부 API만 허용한다. | 기존 비밀번호를 두고 임시 비밀번호를 따로 받는 안. 본인이 모르는 사이에 운영진이 로그인할 수 있다. | 비밀번호를 잊지 않은 사람에게 잘못 발급하면 그 사람은 임시 비밀번호를 받아야 다시 로그인할 수 있다. |
| A10. 처음 관리자는 서버 시작 때 환경변수로 만든다 | 2026-11-05 | 채택 | 빈 DB에서도 PM과 PL이 관리자가 되어야 하고, 비밀값이 코드, 설정 파일, 마이그레이션에 없어야 한다(#23). | 활성 관리자가 0명일 때만 파라미터 스토어의 이메일, 이름, 초기 비밀번호로 `ADMIN` 계정을 만들고 첫 로그인에 비밀번호를 바꾸게 한다. 두 번째 관리자는 첫 관리자가 역할 변경으로 지정한다. | 지정한 이메일로 가입하면 관리자가 되는 안. 메일 인증이 없어 다른 사람이 먼저 가입하면 관리자 자리를 가져간다. 마이그레이션에 넣는 안은 비밀값이 레포에 남는다. | 변수 이름과 형식은 #23에서 정해 배포 문서에 적는다. |
| A11. 로그인 시도 제한은 IP와 이메일 조합으로 하고 계정을 잠그지 않는다 | 2026-11-05 | 채택 | 비밀번호 대입을 막아야 한다. 학교 와이파이처럼 여러 사람이 IP 하나를 쓰는 환경에서 정상 사용자가 막히면 안 된다. | IP와 이메일 조합(5분 10회), 이메일(1시간 50회), IP(5분 200회)의 세 기준. 한도를 넘으면 429. | IP 하나만 기준으로 낮게 거는 안은 같은 와이파이 사용자가 함께 막힌다. 계정 잠금은 남의 계정을 일부러 잠그는 공격이 된다. | 카운터 저장 위치와 로드밸런서 뒤 IP 처리는 PL과 정한다. |
| A12. 관리자 작업은 로그로만 남긴다 | 2026-11-05 | 채택 | 관리자 기능은 누가 무엇을 했는지 남겨야 한다(시큐어 코딩 규칙 1절). | 승인, 거절, 역할 변경, 임시 비밀번호 발급을 처리한 사람 ID, 대상 ID, 결과와 함께 로그로 남긴다. | 감사 테이블을 두는 안. 화면에서 이력을 볼 요구가 없어 MVP에 비해 크다. | 로그 보존 기간이 곧 기록 보존 기간이다(5-4). |
