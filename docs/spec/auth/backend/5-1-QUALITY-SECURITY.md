# 5-1 보안

본 문서는 인증권한 API의 인증 수준과 권한 규칙, 토큰과 비밀번호 처리, 요청 횟수 제한, 입력 검증, 개인정보와 위협 모델을 정한다. 공통 규칙은 시큐어 코딩 규칙을 따른다. ([secure-coding.md](../../../security/secure-coding.md))

<br>

### 5-1-1. 인증 수준

| 수준 | 통과하는 사람 |
|---|---|
| 공개 | 누구나 |
| 로그인 | 활성 계정 모두 <br> 승인 대기 회원 포함 |
| 동아리원 | 역할이 `MEMBER` 이상 |
| 운영진 | 역할이 `STAFF` 이상 |
| 관리자 | 역할이 `ADMIN` |

- 역할 순서는 `PENDING` < `MEMBER` < `STAFF` < `ADMIN`이다. 높은 역할은 낮은 역할의 수준을 모두 통과한다.
- "로그인" 수준은 이 세트의 내 정보 API(조회, 비밀번호 변경, 탈퇴)에만 쓴다. 다른 기능에서 로그인이 필요한 API는 적어도 "동아리원" 수준을 쓴다. 승인 대기 회원은 방문자와 같기 때문이다. (PRODUCT.md 4절)
- 공개라고 명시하지 않은 API는 "동아리원" 수준이 기본이다. 공개 API는 Security 설정의 공개 목록에 하나씩 적는다.

<br>

### 5-1-2. API별 인증 수준과 권한 검사

API 경로는 계약 문서를 따른다. ([4-2-INTERACTION-CONTRACT.md](4-2-INTERACTION-CONTRACT.md))

| API | 인증 수준 | 추가 검사 |
|---|---|---|
| 가입 | 공개 | 요청 횟수 제한 |
| 로그인 | 공개 | 요청 횟수 제한, `Origin` 허용 목록 |
| access 토큰 갱신 | refresh 쿠키 | `Origin` 허용 목록 |
| 로그아웃 | refresh 쿠키 | `Origin` 허용 목록 |
| 내 정보 조회 | 로그인 | 대상은 토큰의 사용자로만 정함 |
| 비밀번호 변경 | 로그인 | 지금 비밀번호 확인, 요청 횟수 제한 |
| 탈퇴 | 로그인 | 지금 비밀번호 확인, 요청 횟수 제한, 마지막 활성 관리자는 거부 |
| 회원 목록 | 운영진 | |
| 가입 승인 | 운영진 | 대상이 `PENDING`일 때만 |
| 가입 거절 | 운영진 | 대상이 `PENDING`일 때만 |
| 역할 변경 | 관리자 | 5-1-3의 역할 변경 규칙 |
| 임시 비밀번호 발급 | 운영진 | 5-1-3의 비밀번호 초기화 규칙 |

<br>

### 5-1-3. 권한 규칙

**역할 변경** (USER-STORIES.md 4절)

- 관리자만 바꾼다.
- 대상은 활성 계정이고 역할이 `MEMBER`, `STAFF`, `ADMIN` 중 하나다. 승인 대기 회원은 대상이 아니다. 역할 변경으로 승인 절차를 건너뛰지 못하게 하려는 것이다.
- 새 역할은 `MEMBER`, `STAFF`, `ADMIN` 중 하나다. `PENDING`으로 내릴 수 없다.
- 활성 관리자가 대상 한 명뿐이면 그 사람의 역할을 내릴 수 없다. 관리자가 자기 역할을 내리는 것은 다른 활성 관리자가 있으면 허용한다.

**비밀번호 초기화** (USER-STORIES.md 6절)

| 요청한 사람 | 대상으로 할 수 있는 사람 |
|---|---|
| 운영진 (`STAFF`) | 역할이 `PENDING`, `MEMBER`인 사람 |
| 관리자 (`ADMIN`) | 자기를 뺀 모든 활성 계정 |

- 자기 자신은 대상이 될 수 없다. 자기 비밀번호는 비밀번호 변경 API로 바꾼다.
- 발급하면 대상의 기존 비밀번호를 임시 비밀번호로 바꾸고 대상의 모든 로그인을 끊는다. 기존 비밀번호를 남겨 두면 운영진이 본인 모르게 그 계정으로 로그인할 수 있기 때문이다. 바꾸면 본인이 다음 로그인에서 알아챈다.

**탈퇴** (USER-STORIES.md 5절)

- 본인만 한다. 경로에 사용자 ID를 받지 않는다.
- 지금 비밀번호를 다시 확인한다. 탈퇴는 되돌릴 수 없으므로, XSS 등으로 access 토큰만 빼앗긴 경우에도 계정이 지워지지 않게 한다.
- 활성 관리자가 자기 한 명뿐이면 거부한다.

**동시 요청**

확인한 뒤 쓰는 작업(로그인, 비밀번호 변경, 임시 비밀번호 발급, 승인과 거절, 역할 변경, 탈퇴)이 동시에 일어날 때의 처리와 잠금은 동시성 문서에서 정한다. 마지막 활성 관리자 확인도 여기에 포함된다. ([5-2-QUALITY-CONCURRENCY.md](5-2-QUALITY-CONCURRENCY.md))

**비밀번호 변경 필요 상태**

access 토큰을 보낸 요청은 아래 API만 통과하고 나머지는 `403 AUTH_PASSWORD_CHANGE_REQUIRED`를 받는다. (USER-STORIES.md 6절)

- 내 정보 조회
- 비밀번호 변경
- access 토큰 갱신
- 로그아웃

### 5-1-4. 요청마다 하는 인증

access 토큰이 있는 요청은 아래 순서로 검사한다. 하나라도 실패하면 거기서 멈춘다.

1. `Authorization: Bearer` 헤더에서 토큰을 꺼낸다. 다른 위치의 토큰은 보지 않는다.
2. 서명 알고리즘을 `HS256`으로 고정해 서명을 검증한다. 헤더의 `alg` 값을 따르지 않는다. `none`과 다른 알고리즘은 거부한다. (CWE-347)
3. `iss`가 `hackhu-hp`인지 확인한다.
4. `exp`가 지났으면 `401 UNAUTHORIZED`를 준다. 응답은 다른 401과 같게 하고, 만료였다는 것은 서버 로그에만 남긴다. (4-2-INTERACTION-CONTRACT.md 4-2-1)
5. `sid`의 로그인 세션과 그 세션의 계정을 DB에서 기본 키로 한 번에 읽는다. 세션이 없거나, 폐기되었거나, 만료되었거나, 세션의 사용자가 `sub`와 다르거나, 계정이 탈퇴했으면 `401 UNAUTHORIZED`를 준다.
6. DB에서 읽은 역할로 현재 사용자를 만든다. 토큰에는 역할을 넣지 않는다.
7. 비밀번호 변경 필요 상태면 5-1-3의 허용 목록만 통과시킨다.

토큰 없이 온 요청은 방문자로 다룬다. 공개 API만 통과한다.

- `Authorization` 헤더가 있는데 `Bearer`가 아니거나 토큰이 비었으면 1단계에서 실패로 본다. 공개 API여도 `401 UNAUTHORIZED`다.
- `/api/v1/auth/**`(가입, 로그인, refresh, 로그아웃)는 이 검사를 하지 않고 헤더를 보지 않는다. 이 API들은 access 토큰을 쓰지 않는다. 만료된 access 토큰이 실린 로그인 요청이 401로 막히지 않게 하려는 것이다. ([DECISIONS.md](DECISIONS.md) A22)
- 실패 이유(서명, 발급자, 만료, 세션 폐기 등)는 DEBUG 로그에만 남긴다. 서명이 틀린 토큰은 누구나 만들 수 있어 높은 수준으로 남기면 로그를 쌓을 수 있다. (CWE-779)

### 5-1-5. 토큰과 쿠키

**access 토큰 (JWT)**

| 항목 | 값 |
|---|---|
| 알고리즘 | `HS256` 고정 |
| 서명 키 | 32바이트 이상 무작위 값 <br> 환경변수로 주입하고 운영에서는 파라미터 스토어에 둠 <br> 값이 없거나 32바이트보다 짧으면 서버가 시작하지 않음 |
| 클레임 | `iss`, `sub`(사용자 ID), `sid`(로그인 세션 ID), `iat`, `exp`만 넣음 <br> 역할, 이메일, 이름을 넣지 않음 |
| 수명 | 15분 |

**서명 키 교체**

- 검증 키는 하나만 둔다. 이전 키로 검증하는 기간을 두지 않는다.
- 키를 바꾸면 그 전에 발급한 access 토큰은 서명 검증에 실패해 `401 UNAUTHORIZED`를 받는다. 프론트엔드는 401이면 코드와 상관없이 refresh를 한 번 시도하므로 새 키로 서명한 access 토큰을 받아 이어서 쓴다. refresh 토큰은 서명 키와 상관없다. (4-2-INTERACTION-CONTRACT.md 4-2-1)
- 키가 유출되어 급히 바꿀 때도 절차가 같다. 사용자는 로그아웃되지 않는다.
- 키를 바꾸는 절차(파라미터 스토어 값 교체 후 재배포)는 배포 문서에 적는다.

access 토큰의 무효화는 발급 시각이 아니라 로그인 세션의 폐기 여부로 판단한다. 로그아웃, 비밀번호 변경, 비밀번호 초기화, 재사용 감지는 세션을 폐기하므로, 그 세션에서 발급한 access 토큰은 만료 전이라도, 같은 초에 발급되었더라도 다음 요청부터 거부된다. (CWE-613)

**refresh 토큰**

- `SecureRandom`으로 만든 32바이트 값을 Base64URL로 인코딩한다. JWT가 아니다.
- DB에는 SHA-256 해시만 저장한다. (3-2-DESIGN-DB-SCHEMA.md)
- 쓸 때마다 회전한다. 동시 요청과 응답 유실은 복구하고, 그 밖의 재사용은 탈취로 보고 로그인 세션을 폐기한다. 판단 규칙은 계약 문서를 따른다. (4-2-INTERACTION-CONTRACT.md 4-2-5)
- 쿠키 속성은 `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api/v1/auth`다. (4-2-INTERACTION-CONTRACT.md) `Domain` 속성은 두지 않는다. API 호스트에만 실리고 같은 등록 도메인의 다른 서브도메인에는 실리지 않게 하려는 것이다.
- `SameSite=Strict`는 프론트엔드와 API가 같은 등록 도메인 아래 서브도메인에 있다는 전제에서만 동작한다(예: `www.hackhu.example`과 `api.hackhu.example`). 등록 도메인이 다르면 브라우저가 refresh와 로그아웃 요청에 쿠키를 싣지 않아, 로그인 뒤 15분이 지나면 모두 로그아웃된다. 도메인 구조는 배포 문서에서 확정한다. ([DEPLOYMENT.md](../../DEPLOYMENT.md)) 배포 도메인을 바꾸면 이 절을 다시 본다. 다른 사이트로 가야 하면 `SameSite=None`과 CSRF 토큰을 함께 써야 한다.

**CSRF**

- access 토큰은 헤더로만 받으므로 그 API들은 CSRF 대상이 아니다.
- 쿠키를 쓰는 refresh와 로그아웃은 `SameSite=Strict`에 더해 `Origin` 헤더가 허용 목록(프론트엔드 주소)에 있는지 확인한다. 없거나 다르면 거부한다.
- 쿠키를 새로 주는 로그인도 `Origin` 허용 목록을 확인하고 JSON 본문만 받는다. 다른 사이트가 폼으로 피해자의 브라우저를 공격자 계정에 로그인시키는 것(로그인 CSRF)을 막는다. (4-2-INTERACTION-CONTRACT.md 4-2-4)
- CORS는 모든 API에서 프론트엔드 주소 하나만 허용하고 `Access-Control-Allow-Credentials: true`를 준다. `*`를 쓰지 않는다. 프론트엔드가 모든 요청에 `credentials: 'include'`를 붙이기 때문이다. (4-2-INTERACTION-CONTRACT.md 4-2-1)
- CORS는 메서드 `GET`, `POST`, `PUT`, `DELETE`와 요청 헤더 `Authorization`, `Content-Type`만 허용한다.
- CORS 응답에 `Access-Control-Expose-Headers: Retry-After, Location`을 준다. 출처가 다르면 이 헤더 없이는 프론트엔드가 429의 대기 시간과 가입 응답의 위치를 읽지 못한다.

**노출 방지**

- 토큰을 URL, 로그, 에러 응답에 넣지 않는다.
- 토큰이나 임시 비밀번호를 담은 응답에는 `Cache-Control: no-store`를 붙인다.

### 5-1-6. 비밀번호

**저장**

- bcrypt, cost 12로 해시한다. (CWE-916)
- 로그인할 때 이메일이 없는 경우에도 미리 만든 더미 해시와 비교해 응답 시간을 맞춘다. 응답 시간으로 계정이 있는지 알 수 없게 하려는 것이다. (CWE-208)

**규칙** (USER-STORIES.md 1절이 인증권한팀에 맡긴 것)

| 규칙 | 값 |
|---|---|
| 길이 | 10자 이상 64자 이하 |
| 바이트 | UTF-8로 72바이트 이하 <br> bcrypt가 72바이트 뒤를 버리기 때문 |
| 이메일과 같음 | 거부 (대소문자 무시) |
| 조합 규칙 | 두지 않음 <br> 숫자와 특수문자를 강제하지 않음 |

조합 규칙 대신 길이를 요구한다. 조합을 강제하면 `Password1!`처럼 예측하기 쉬운 비밀번호가 늘어나기 때문이다. (NIST SP 800-63B)

**임시 비밀번호**

- `SecureRandom`으로 16자를 만든다. 헷갈리는 문자(`0`, `O`, `1`, `l`, `I`)는 쓰지 않는다.
- 원문은 발급 응답에서 한 번만 주고 로그에 남기지 않는다.
- 유효 시간과 횟수는 USER-STORIES.md 6절을 따른다. 처음 로그인하면 `temp_password_used_at`을 기록하고, 그 뒤에는 같은 임시 비밀번호로 로그인할 수 없다. 이미 받은 로그인 상태로는 비밀번호를 바꿀 수 있다.
- 사용 여부 확인과 기록은 검증한 해시를 조건에 넣은 조건부 갱신 하나로 해서, 동시 로그인과 재발급 경합에서도 한 번만 성공시킨다. 쿼리와 처리는 동시성 문서에 있다. ([5-2-QUALITY-CONCURRENCY.md](5-2-QUALITY-CONCURRENCY.md)) (CWE-362)

**검증 뒤 비밀번호가 바뀌는 경우**

로그인, 비밀번호 변경, 탈퇴는 비밀번호를 검증한 뒤 쓰기 직전에 그 해시가 아직 현재 값인지 다시 확인한다. 검증과 쓰기 사이에 비밀번호가 바뀌거나 초기화되면 요청을 실패시킨다. 그래야 옛 비밀번호로 만든 세션이 남지 않는다. 방법은 동시성 문서를 따른다. (5-2-QUALITY-CONCURRENCY.md 5-2-3)

**처음 관리자** (#23)

- 서버가 시작할 때 활성 관리자가 0명이면, 환경변수로 받은 이메일, 이름, 초기 비밀번호로 `ADMIN` 계정을 만든다. 운영에서는 이 값을 파라미터 스토어에 둔다.
- 만든 계정은 비밀번호 변경 필요 상태로 시작한다. 첫 로그인에서 비밀번호를 바꿔야 한다.
- 활성 관리자가 한 명이라도 있으면 아무것도 하지 않는다. 서버 여러 대가 동시에 시작해도 한 번만 만든다. (5-2-QUALITY-CONCURRENCY.md 5-2-2) 계정을 만든 뒤에는 초기 비밀번호 값을 파라미터 스토어에서 지운다.
- "이 이메일로 가입하면 관리자가 된다"는 방식은 쓰지 않는다. 메일 인증이 없어서 다른 사람이 그 이메일로 먼저 가입하면 관리자 자리를 가져간다.
- 환경변수 이름과 형식은 #23에서 정하고 배포 문서에 적는다.

### 5-1-7. 요청 횟수 제한

(CWE-307)

| API | 기준 | 한도 | 세는 것 |
|---|---|---|---|
| 로그인 | IP와 이메일 조합 | 5분에 10회 | 실패한 시도 |
| 로그인 | IP | 5분에 200회 | 모든 시도 |
| 가입 | IP | 1시간에 50회 | 모든 시도 |
| 비밀번호 변경, 탈퇴 | 사용자 ID | 5분에 10회 (두 API 합산) | 지금 비밀번호가 틀린 시도 |

- 한도를 넘으면 `429`와 `Retry-After` 헤더를 준다. 값은 창이 끝날 때까지 남은 초다.
- 실패만 세는 기준(로그인의 IP와 이메일 조합, 비밀번호 변경과 탈퇴)은 비밀번호를 확인하기 전에 한 번을 세어 두고, 비밀번호가 맞으면 되돌린다. 확인한 뒤에 세면 동시에 들어온 시도가 모두 확인을 통과해 한도를 넘는다. ([DECISIONS.md](DECISIONS.md) A21)
- 가입은 본문 검증(400)을 통과한 요청을 센다. 검증에서 끝나는 요청은 bcrypt를 계산하지 않는다.
- 요청 제한 걸림 로그는 창마다 처음 거부할 때만 남긴다. 거부할 때마다 남기면 누구나 로그를 쌓을 수 있다. (CWE-779)
- 로그인 실패는 가입되지 않은 이메일이어도 똑같이 센다. 다르게 세면 제한에 걸리는지로 계정이 있는지 알 수 있다.
- 계정을 잠그지 않고, 이메일만을 기준으로 한 제한도 두지 않는다. 둘 다 공격자가 남의 이메일로 일부러 실패해 그 사람이 어디서도 로그인하지 못하게 만들 수 있다. 위의 기준은 모두 IP가 들어가므로 공격자의 IP만 막히고, 피해자는 다른 IP에서 계속 로그인할 수 있다.
- 이메일만 기준으로 세는 것은 막지 않고 감지에만 쓴다. 한 계정에 1시간 동안 여러 IP에서 50회 넘게 실패하면 경고 로그를 남기고 운영진에게 알린다. 경고 로그는 넘는 순간 한 번만 남기고, 가입된 계정의 실패만 센다. 같은 계정의 실패가 동시에 들어와도 정확히 한 번 남도록 세기와 판정을 한 원자적 단계에서 한다. 알림 방법은 관측 문서에서 정한다. 그 전까지는 경고 로그만 남는다. ([5-4-QUALITY-OBSERVABILITY.md](5-4-QUALITY-OBSERVABILITY.md)) 운영진은 그 계정 주인에게 알리고 필요하면 비밀번호 초기화를 안내한다.
- IP 하나 기준의 한도는 학교 와이파이처럼 여러 사람이 IP를 공유해도 걸리지 않게 넉넉히 잡는다. (2-REQUIREMENTS.md)
- 클라이언트 IP는 아래 규칙으로만 정한다. (CWE-348)
  1. 연결 상대의 주소(`request.getRemoteAddr()`)가 신뢰하는 프록시 대역(설정값, 운영에서는 로드밸런서 서브넷의 CIDR)에 없으면 그 주소를 쓰고 `X-Forwarded-For`는 보지 않는다.
  2. 신뢰하는 프록시 대역에서 온 연결이면 `X-Forwarded-For` 목록을 오른쪽부터 본다. 신뢰 홉 수가 N(설정값, 로드밸런서만 있으면 1)이면 오른쪽에서 N번째 값을 쓴다.
  3. 헤더가 없거나, 항목이 N개보다 적거나, IP 형식이 아니면 연결 상대의 주소를 쓰고 경고 로그를 남긴다.
- 이 헤더는 쉼표로 이은 목록이고, 맨 왼쪽부터는 클라이언트가 직접 보낸 값이 그대로 남는다. 로드밸런서는 자기에게 연결한 주소를 맨 오른쪽에 덧붙이므로 오른쪽 값만 믿을 수 있다.
- Spring의 `ForwardedHeaderFilter`(`server.forward-headers-strategy=framework`)를 쓰지 않는다. 이 필터는 어떤 프록시를 믿을지 검사하지 않고 헤더 값을 그대로 요청 주소로 바꾼다. `Forwarded`, `X-Real-IP` 헤더도 보지 않는다.
- 이 규칙은 두 가지 인프라 전제에 기댄다. 하나는 앱이 로드밸런서 보안 그룹에서 오는 연결만 받는 것이고, 다른 하나는 로드밸런서의 `X-Forwarded-For` 처리 방식이 기본값(append)인 것이다. preserve로 바꾸면 클라이언트가 보낸 값이 그대로 넘어와 위조할 수 있다. 신뢰 대역, 홉 수와 이 전제는 배포 문서에 적는다.
- 카운터는 서버 메모리에 둔다. 인스턴스가 하나라 분산 카운터가 필요 없고, 갤러리의 업로드 주소 발급 제한도 같은 방식이다. 인메모리라서 생기는 한계는 아래와 같고, 지금 규모에서는 받아들인다.
  - 재배포하면 카운터가 초기화되어 배포 직후에는 제한이 처음부터 다시 센다.
  - 인스턴스를 둘 이상으로 늘리면 한도가 인스턴스 수만큼 느슨해진다. 그때 Redis나 WAF로 옮긴다.
- 카운터는 창(5분, 1시간)이 지나면 저절로 지워지는 캐시에 두고, 항목 수 상한을 10만 개로 둔다. 무작위 이메일로 요청해 메모리를 채우는 것을 막는다. IP 기준 한도(5분에 200회)가 IP 하나가 만들 수 있는 항목 수를 묶으므로, 상한에 닿아 다른 카운터가 밀려나려면 많은 IP가 필요하다.

### 5-1-8. 입력 검증

- 요청 DTO는 계약 문서에 적힌 필드만 가진다. `role`을 받는 DTO는 역할 변경 요청 하나뿐이고 관리자 검사 뒤에만 쓴다. 가입과 내 정보 DTO에는 `role`, `id`, `approvedAt`이 없다. (CWE-915)
- 이메일은 앞뒤 공백을 지우고 `Locale.ROOT`로 소문자로 바꾼 뒤 형식과 길이를 검사한다. ASCII 문자만 받는다. ASCII 밖의 문자는 Java와 PostgreSQL의 소문자 변환 결과가 달라 `ck_users_email_lower` 위반이나 중복 가입이 생길 수 있기 때문이다.
- 이름은 앞뒤 공백을 지운 뒤 길이를 검사하고 제어 문자, 줄과 문단 구분 문자(U+2028, U+2029), 양방향 텍스트 제어 문자(U+202A~U+202E, U+2066~U+2069, U+200E, U+200F, U+061C)를 거부한다. 양방향 제어 문자는 Unicode의 Bidi_Control 속성 전체다. 양방향 제어 문자는 화면에 보이는 이름을 뒤집어 다른 사람처럼 보이게 할 수 있다. 이름은 다른 사람 화면에 보이므로 프론트엔드가 출력할 때 이스케이프한다. (CWE-79)
- 경로의 `userId`는 숫자만 받는다.
- 회원 목록의 `role`과 `sort`는 허용 목록으로 검사한다.

### 5-1-9. 개인정보

| 정보 | 받는 이유 | 볼 수 있는 사람 |
|---|---|---|
| 이메일 | 로그인 ID | 본인, 운영진 이상(회원 목록) |
| 이름 | 승인할 때 누구인지 확인, 작성자 표시 | 본인, 운영진 이상(회원 목록), 다른 기능의 작성자 표시 |
| 비밀번호 | 로그인 | 아무도 볼 수 없음 <br> 해시만 저장함 |

- 다른 기능의 응답에는 작성자의 이름만 넣고 이메일을 넣지 않는다.
- 탈퇴하면 이메일, 이름, 비밀번호 해시를 즉시 지운다. (3-2-DESIGN-DB-SCHEMA.md)
- 로그에는 사용자 ID만 남긴다. 이메일, 이름, 비밀번호, 토큰, 임시 비밀번호를 남기지 않는다. 로그인 실패 로그에도 입력한 이메일을 남기지 않는다. 비밀번호를 이메일 칸에 잘못 입력하는 경우가 있기 때문이다. (CWE-532)
- DB 제약 위반의 오류 상세(예: `Key (email)=(...) already exists`)는 행 값을 담으므로 예외 메시지와 로그에 싣지 않는다. PostgreSQL JDBC 드라이버의 `logServerErrorDetail`을 `false`로 둔다. 제약 이름은 남는다. (CWE-532)
