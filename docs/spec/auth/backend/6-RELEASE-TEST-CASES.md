# 6 테스트 케이스

본 문서는 인증권한 백엔드의 테스트 케이스와 실행 결과를 정한다. 지금은 설계 단계에서 정한 토큰 무효화, refresh 회전, 쿠키 전달, 임시 비밀번호, 요청 횟수 제한, 동시성, 탈퇴와 입력 검증 케이스만 있다. 나머지 케이스, 실행 명령과 통과 증거는 구현 이슈에서 채운다.

<br>

### 6-1. 토큰 무효화

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| T1 | 로그아웃한 뒤 그 세션에서 받은 만료 전 access 토큰으로 동아리원 API를 부름 | 401 `UNAUTHORIZED` | 미실행 |
| T2 | 기기 A에서 로그아웃한 뒤 기기 B의 access 토큰으로 부름 | 200 <br> 다른 세션은 유지됨 | 미실행 |
| T3 | 비밀번호 변경과 같은 초에 발급된 이전 access 토큰으로 부름 | 401 `UNAUTHORIZED` | 미실행 |
| T4 | 비밀번호 변경 응답으로 받은 새 access 토큰으로 부름 | 200 | 미실행 |
| T5 | 임시 비밀번호를 발급받은 대상의 이전 access 토큰으로 부름 | 401 `UNAUTHORIZED` | 미실행 |
| T6 | 역할을 `STAFF`에서 `MEMBER`로 내린 직후 같은 access 토큰으로 운영진 API를 부름 | 403 | 미실행 |
| T7 | 탈퇴한 뒤 이전 access 토큰으로 부름 | 401 `UNAUTHORIZED` | 미실행 |
| T8 | 서명 키를 바꾼 뒤 이전 access 토큰으로 부르고, 프론트엔드 규칙대로 refresh 후 다시 보냄 | 첫 요청 401 `UNAUTHORIZED` <br> refresh 200 <br> 다시 보낸 요청 200 | 미실행 |
| T9 | 다시 보낸 요청도 401을 받음 | refresh를 다시 부르지 않고 로그인 화면으로 감 (프론트엔드) | 미실행 |
| T10 | 탭 A가 사용자 A로 글 작성 요청을 보내 401을 받기 전에, 탭 B가 사용자 B로 로그인함 | 탭 A의 refresh 응답 `user.id`가 B라서 작성 요청을 다시 보내지 않음 <br> 글이 B 명의로 저장되지 않음 <br> 탭 A는 B로 화면을 다시 그리고 입력은 남김 (프론트엔드) | 미실행 |
| T11 | T10과 같은 상황에서 조회 요청이 401을 받음 | 조회 요청을 다시 보내지 않음 (프론트엔드) | 미실행 |
| T12 | 만료된 access 토큰과 서명이 틀린 토큰으로 각각 부름 | 둘 다 같은 401 `UNAUTHORIZED` 응답 <br> 만료 여부는 서버 로그에만 남음 | 미실행 |
| T13 | 로그인한 브라우저에서 다시 로그인함 (기존 refresh 쿠키가 실림) | 기존 세션이 폐기됨 <br> 기존 세션의 access 토큰은 401 | 미실행 |

### 6-2. refresh 회전

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| R1 | 현재 토큰으로 갱신 | 200, 새 쿠키 | 미실행 |
| R2 | 같은 토큰으로 두 요청을 동시에 보냄 | 둘 다 200 <br> 한 응답만 새 쿠키를 줌 <br> 이후 브라우저의 쿠키로 갱신하면 200 | 미실행 |
| R3 | 갱신 응답을 받지 못한 뒤 10초 안에 같은 토큰으로 다시 갱신 | 200, 새 쿠키 없음 | 미실행 |
| R4 | 갱신 응답을 받지 못한 뒤 10초가 지나 같은 토큰으로 다시 갱신 | 200, 새 쿠키 <br> 이후 새 쿠키로 갱신하면 200 | 미실행 |
| R5 | 두 번 회전한 뒤, 처음 토큰이 회전한 지 10초가 지나서 처음 토큰으로 갱신 | 401, 세션 폐기 <br> 그 세션의 access 토큰도 401 <br> 10초 안이면 R8과 같이 200 | 미실행 |
| R6 | R4의 복구로 폐기된 토큰으로 갱신 | 401, 세션 폐기 | 미실행 |
| R7 | 로그인 30일이 지난 세션의 토큰으로 갱신 | 401 | 미실행 |
| R8 | 탭 A가 T0로 T1을 받고 곧바로 T1로 T2를 받은 뒤, 탭 B의 T0 요청이 10초 안에 늦게 처리됨 | 탭 B도 200, 새 쿠키 없음 <br> 세션 유지 | 미실행 |
| R9 | 갱신 응답을 받지 못한 뒤 하루가 지나(14일 안) 같은 토큰으로 갱신 | 200, 새 쿠키 | 미실행 |
| R10 | 두 번 회전한 지 하루가 지난 예전 토큰을 다시 씀 | 401, 세션 폐기 | 미실행 |

<br>

### 6-3. 쿠키 전달

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| C1 | 프론트엔드와 API 주소가 다른 환경에서 `credentials: 'include'`로 로그인한 뒤 refresh | 200 | 미실행 |
| C2 | 같은 환경에서 비밀번호를 바꾼 뒤 refresh | 200 <br> 새 세션의 쿠키로 갱신됨 | 미실행 |
| C3 | 같은 환경에서 429를 받음 | 프론트엔드 JavaScript가 `Retry-After` 값을 읽음 | 미실행 |
| C4 | 다른 사이트의 `enctype="text/plain"` 폼으로 JSON처럼 보이는 로그인 본문을 보냄 | 415 <br> 세션과 쿠키가 생기지 않음 | 미실행 |
| C5 | 허용 목록에 없는 `Origin`으로 로그인, refresh, 로그아웃을 부름 | 모두 403 <br> 세션이 바뀌지 않음 | 미실행 |
| C6 | 로그인 응답의 `Set-Cookie`를 확인 | `Domain` 속성이 없음, `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api/v1/auth`가 있음 | 미실행 |

### 6-4. 임시 비밀번호

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| TP1 | 같은 임시 비밀번호로 로그인 요청 두 개를 동시에 보냄 | 하나만 200, 다른 하나는 401 <br> 세션은 하나만 생김 | 미실행 |
| TP2 | 임시 비밀번호로 로그인한 뒤 같은 임시 비밀번호로 다시 로그인 | 401 | 미실행 |
| TP3 | 옛 임시 비밀번호의 검증이 끝난 직후, 사용 기록 전에 운영진이 새 임시 비밀번호를 발급함 | 옛 임시 비밀번호 로그인은 401, 세션이 생기지 않음 <br> 새 임시 비밀번호는 사용 전 상태로 남아 로그인됨 | 미실행 |

<br>

### 6-5. 요청 횟수 제한

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| L1 | IP A에서 한 이메일로 5분에 11번 실패 | 11번째에 429 | 미실행 |
| L2 | L1 직후 IP B에서 같은 이메일로 맞는 비밀번호로 로그인 | 200 | 미실행 |
| L3 | 여러 IP에서 한 이메일로 1시간에 51번 실패 | 로그인은 막지 않고 경고 로그가 남음 | 미실행 |
| L4 | 신뢰 프록시를 거친 요청에 매번 다른 위조 `X-Forwarded-For` 값을 앞에 붙여 한 이메일로 11번 실패 | 모두 같은 IP로 세어 11번째에 429 | 미실행 |
| L5 | 신뢰 프록시 대역 밖에서 직접 연결하고 `X-Forwarded-For`를 붙임 | 헤더를 무시하고 연결 상대의 주소로 셈 | 미실행 |
| L6 | 가입되지 않은 이메일로 5분에 11번 실패 | L1과 같이 11번째에 429 | 미실행 |
| L7 | 비밀번호 변경과 탈퇴에서 지금 비밀번호를 합쳐 5분에 11번 틀림 | 11번째에 429 | 미실행 |

### 6-6. 동시성

케이스마다 두 작업의 순서를 바꿔 가며 확인한다. 기대는 어느 순서로 끝나도 같아야 한다. ([5-2-QUALITY-CONCURRENCY.md](5-2-QUALITY-CONCURRENCY.md))

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| CC1 | 일반 로그인의 비밀번호 검증이 끝난 직후 운영진이 그 사람의 비밀번호를 초기화함 | 옛 비밀번호로 만든 세션이 살아 있지 않음 <br> 로그인이 401이거나, 만들어진 세션이 초기화로 폐기됨 | 미실행 |
| CC2 | CC1과 같은 순간에 다른 기기에서 비밀번호를 바꿈 | CC1과 같음 | 미실행 |
| CC3 | CC1과 같은 순간에 그 계정이 탈퇴함 | 세션이 남지 않음 | 미실행 |
| CC4 | 같은 사용자가 두 기기에서 같은 지금 비밀번호로 동시에 비밀번호를 바꿈 | 하나만 200, 다른 하나는 400 | 미실행 |
| CC5 | 승인과 거절을 동시에 보냄 | 하나만 성공, 다른 하나는 404나 409 | 미실행 |
| CC6 | 활성 관리자 둘이 동시에 서로의 역할을 `MEMBER`로 내림 | 하나만 성공, 다른 하나는 409 <br> 활성 관리자가 1명 이상 남음 | 미실행 |
| CC7 | 활성 관리자 둘 중 한 명은 탈퇴하고 다른 한 명은 자기 역할을 내림 | 하나만 성공 <br> 활성 관리자가 1명 이상 남음 | 미실행 |
| CC8 | 운영진의 임시 비밀번호 발급 권한 검사 직후 대상이 `STAFF`로 승격됨 | 발급이 403 <br> 대상의 비밀번호와 세션이 바뀌지 않음 | 미실행 |
| CC9 | 서버 두 대가 빈 DB에서 동시에 시작함 | 처음 관리자가 한 명만 생김 | 미실행 |
| CC10 | 같은 이메일로 동시에 가입함 | 하나만 201, 다른 하나는 409 <br> 500이 나지 않음 | 미실행 |
| CC11 | 관리자 A가 `STAFF`인 X를 `ADMIN`으로 올리는 동안 관리자 B가 X를 `MEMBER`로 내림 | 내리는 쪽은 X가 관리자가 되었으면 마지막 관리자 확인을 거침 <br> 활성 관리자가 1명 이상 남음 | 미실행 |
| CC12 | 임시 비밀번호로 한 번 로그인한 뒤 같은 임시 비밀번호로 다시 로그인 | 401 <br> 일반 로그인 경로로 통과하지 않음 | 미실행 |
| CC13 | 관리자가 A 한 명일 때, `MEMBER`인 X의 탈퇴가 역할을 읽은 직후 멈춘 사이 A가 X를 `ADMIN`으로 올리고 자기 역할을 `MEMBER`로 내린 뒤 X의 탈퇴가 진행됨 | X의 탈퇴는 409 <br> X가 활성 관리자로 남아 활성 관리자가 1명 | 미실행 |
| CC14 | 관리자가 A와 X 둘일 때, X의 탈퇴가 관리자 잠금을 잡은 사이 A가 자기 역할을 내림 | X의 탈퇴는 204 <br> A의 강등은 잠금을 기다린 뒤 A가 마지막 관리자라 409 <br> 활성 관리자가 1명 | 미실행 |

### 6-7. 탈퇴와 입력 검증

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| W1 | 비밀번호 없이, 또는 틀린 비밀번호로 탈퇴 | 400, 계정이 그대로 있음 | 미실행 |
| W2 | 맞는 비밀번호로 탈퇴 | 204, 이메일, 이름, 비밀번호 해시가 NULL <br> 이전 access 토큰과 refresh 쿠키가 401 | 미실행 |
| W3 | 마지막 활성 관리자가 맞는 비밀번호로 탈퇴 | 409, 계정이 그대로 있음 | 미실행 |
| I1 | ASCII가 아닌 문자가 든 이메일로 가입 | 400 | 미실행 |
| I2 | 양방향 텍스트 제어 문자가 든 이름으로 가입 | 400 | 미실행 |
| I3 | 서명 키 없이, 또는 32바이트보다 짧은 키로 서버를 시작 | 시작하지 않음 | 미실행 |

### 6-8. 경로별 인증 수준과 거부 응답

Security 설정(#21)의 경로 규칙과 401, 403 응답 형식을 본다. 실제 토큰 없이 테스트용 사용자로 역할만 바꿔 부른다. 토큰 검증은 6-1에서 본다.

실행: `cd backend && ./gradlew test --tests 'com.hackhu.hp.global.security.SecurityConfigTest'` (`SecurityConfigTest`)

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| S1 | 로그인하지 않고 동아리원 API를 부름 | 401 `UNAUTHORIZED` | 통과 |
| S2 | 승인 대기 회원이 동아리원 API를 부름 | 403 `FORBIDDEN` | 통과 |
| S3 | 운영진과 관리자가 동아리원 API를 부름 | 200 | 통과 |
| S4 | 로그인하지 않고 없는 경로를 부름 | 401 `UNAUTHORIZED` <br> 경로가 있는지 드러나지 않음 | 통과 |
| S5 | 로그인하지 않고 로그인 API를 CSRF 토큰 없이 부름 | 통과, `Set-Cookie` 없음(서버 세션 없음) | 통과 |
| S6 | 로그인 API 경로를 GET으로 부름 | 401 <br> 공개 목록은 메서드별임 | 통과 |
| S7 | 승인 대기 회원이 내 정보 조회, 비밀번호 변경, 탈퇴를 부름 | 200 | 통과 |
| S8 | 승인 대기 회원이 `/api/v1/users/me` 아래의 다른 경로를 부름 | 403 `FORBIDDEN` | 통과 |
| S9 | 동아리원이 관리 API(`/api/v1/admin/**`)를 부름 | 403 `FORBIDDEN` | 통과 |
| S10 | 운영진이 역할 변경 API를 부름 | 403 `FORBIDDEN` <br> 관리자는 200 | 통과 |
| S11 | `@PreAuthorize`에서 거부됨 | 로그인하지 않았으면 401, 역할이 부족하면 403 <br> 500이 아님 | 통과 |
| S12 | 프론트엔드 주소에서 CORS 사전 요청 | 허용, `Access-Control-Allow-Credentials: true` | 통과 |
| S13 | 다른 주소에서, 또는 허용하지 않은 메서드(`PATCH`)로 CORS 사전 요청 | 403 | 통과 |
