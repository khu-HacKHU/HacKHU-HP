# 6 테스트 케이스

본 문서는 인증권한 백엔드의 테스트 케이스와 실행 결과를 정한다. 지금은 설계 단계에서 정한 토큰 무효화, refresh 회전, 쿠키 전달, 임시 비밀번호, 요청 횟수 제한 케이스만 있다. 나머지 케이스, 실행 명령과 통과 증거는 구현 이슈에서 채운다.

<br>

### 6-1. 토큰 무효화

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| T1 | 로그아웃한 뒤 그 세션에서 받은 만료 전 access 토큰으로 동아리원 API를 부름 | 401 `UNAUTHORIZED` | 미실행 |
| T2 | 기기 A에서 로그아웃한 뒤 기기 B의 access 토큰으로 부름 | 200 <br> 다른 세션은 유지됨 | 미실행 |
| T3 | 비밀번호 변경과 같은 초에 발급된 이전 access 토큰으로 부름 | 401 `UNAUTHORIZED` | 미실행 |
| T4 | 비밀번호 변경 응답으로 받은 새 access 토큰으로 부름 | 200 | 미실행 |
| T5 | 임시 비밀번호를 발급받은 대상의 이전 access 토큰으로 부름 | 401 `UNAUTHORIZED` | 미실행 |
| T6 | 역할을 `STAFF`에서 `MEMBER`로 내린 직후 같은 access 토큰으로 운영진 API를 부름 | 403 | 미실행 |
| T7 | 탈퇴한 뒤 이전 access 토큰으로 부름 | 401 `UNAUTHORIZED` | 미실행 |
| T8 | 서명 키를 바꾼 뒤 이전 access 토큰으로 부르고, 프론트엔드 규칙대로 refresh 후 다시 보냄 | 첫 요청 401 `UNAUTHORIZED` <br> refresh 200 <br> 다시 보낸 요청 200 | 미실행 |
| T9 | 다시 보낸 요청도 401을 받음 | refresh를 다시 부르지 않고 로그인 화면으로 감 (프론트엔드) | 미실행 |
| T10 | 탭 A가 사용자 A로 글 작성 요청을 보내 401을 받기 전에, 탭 B가 사용자 B로 로그인함 | 탭 A의 refresh 응답 `user.id`가 B라서 작성 요청을 다시 보내지 않음 <br> 글이 B 명의로 저장되지 않음 <br> 탭 A는 B로 화면을 다시 그리고 입력은 남김 (프론트엔드) | 미실행 |
| T11 | T10과 같은 상황에서 조회 요청이 401을 받음 | 조회 요청을 다시 보내지 않음 (프론트엔드) | 미실행 |
| T12 | 만료된 access 토큰과 서명이 틀린 토큰으로 각각 부름 | 둘 다 같은 401 `UNAUTHORIZED` 응답 <br> 만료 여부는 서버 로그에만 남음 | 미실행 |

<br>

### 6-2. refresh 회전

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| R1 | 현재 토큰으로 갱신 | 200, 새 쿠키 | 미실행 |
| R2 | 같은 토큰으로 두 요청을 동시에 보냄 | 둘 다 200 <br> 한 응답만 새 쿠키를 줌 <br> 이후 브라우저의 쿠키로 갱신하면 200 | 미실행 |
| R3 | 갱신 응답을 받지 못한 뒤 10초 안에 같은 토큰으로 다시 갱신 | 200, 새 쿠키 없음 | 미실행 |
| R4 | 갱신 응답을 받지 못한 뒤 10초가 지나 같은 토큰으로 다시 갱신 | 200, 새 쿠키 <br> 이후 새 쿠키로 갱신하면 200 | 미실행 |
| R5 | 두 번 회전한 뒤, 처음 토큰이 회전한 지 10초가 지나서 처음 토큰으로 갱신 | 401, 세션 폐기 <br> 그 세션의 access 토큰도 401 <br> 10초 안이면 R8과 같이 200 | 미실행 |
| R6 | R4의 복구로 폐기된 토큰으로 갱신 | 401, 세션 폐기 | 미실행 |
| R7 | 로그인 30일이 지난 세션의 토큰으로 갱신 | 401 | 미실행 |
| R8 | 탭 A가 T0로 T1을 받고 곧바로 T1로 T2를 받은 뒤, 탭 B의 T0 요청이 10초 안에 늦게 처리됨 | 탭 B도 200, 새 쿠키 없음 <br> 세션 유지 | 미실행 |
| R9 | 갱신 응답을 받지 못한 뒤 하루가 지나(14일 안) 같은 토큰으로 갱신 | 200, 새 쿠키 | 미실행 |
| R10 | 두 번 회전한 지 하루가 지난 예전 토큰을 다시 씀 | 401, 세션 폐기 | 미실행 |

<br>

### 6-3. 쿠키 전달

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| C1 | 프론트엔드와 API 주소가 다른 환경에서 `credentials: 'include'`로 로그인한 뒤 refresh | 200 | 미실행 |
| C2 | 같은 환경에서 비밀번호를 바꾼 뒤 refresh | 200 <br> 새 세션의 쿠키로 갱신됨 | 미실행 |
| C3 | 같은 환경에서 429를 받음 | 프론트엔드 JavaScript가 `Retry-After` 값을 읽음 | 미실행 |

<br>

### 6-4. 임시 비밀번호

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| TP1 | 같은 임시 비밀번호로 로그인 요청 두 개를 동시에 보냄 | 하나만 200, 다른 하나는 401 <br> 세션은 하나만 생김 | 미실행 |
| TP2 | 임시 비밀번호로 로그인한 뒤 같은 임시 비밀번호로 다시 로그인 | 401 | 미실행 |
| TP3 | 옛 임시 비밀번호의 검증이 끝난 직후, 사용 기록 전에 운영진이 새 임시 비밀번호를 발급함 | 옛 임시 비밀번호 로그인은 401, 세션이 생기지 않음 <br> 새 임시 비밀번호는 사용 전 상태로 남아 로그인됨 | 미실행 |

<br>

### 6-5. 요청 횟수 제한

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| L1 | IP A에서 한 이메일로 5분에 11번 실패 | 11번째에 429 | 미실행 |
| L2 | L1 직후 IP B에서 같은 이메일로 맞는 비밀번호로 로그인 | 200 | 미실행 |
| L3 | 여러 IP에서 한 이메일로 1시간에 51번 실패 | 로그인은 막지 않고 경고 로그가 남음 | 미실행 |
