# 6 테스트 케이스

본 문서는 인증권한 백엔드의 테스트 케이스와 실행 결과를 정한다. 6-1~6-7은 설계 단계에서 정한 케이스이고, 구현한 이슈에서 실행해 상태를 채운다. 아직 만들지 않은 API(비밀번호 변경, 탈퇴, 승인, 역할 변경, 임시 비밀번호 발급)와 프론트엔드의 케이스는 미실행이다.

6-1~6-7 가운데 로그인, refresh, 로그아웃(#25)으로 실행한 것: `cd backend && ./gradlew test --tests 'com.hackhu.hp.domain.auth.*' --tests 'com.hackhu.hp.global.auth.*' --tests 'com.hackhu.hp.global.security.*'` (`LoginLogoutIntegrationTest`, `TokenRefreshIntegrationTest`, `LoginRateLimitIntegrationTest`, `AccessTokenServiceTest`, `ClientIpResolverTest`, `RateLimiterTest`). DB가 필요한 테스트는 Testcontainers로 PostgreSQL 17을 띄우므로 Docker가 필요하다.

### 6-1. 토큰 무효화

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|

| T2 | 기기 A에서 로그아웃한 뒤 기기 B의 access 토큰으로 부름 | 200 <br> 다른 세션은 유지됨 | 통과 |
| T3 | 비밀번호 변경과 같은 초에 발급된 이전 access 토큰으로 부름 | 401 `UNAUTHORIZED` | 미실행 |
| T4 | 비밀번호 변경 응답으로 받은 새 access 토큰으로 부름 | 200 | 미실행 |
| T5 | 임시 비밀번호를 발급받은 대상의 이전 access 토큰으로 부름 | 401 `UNAUTHORIZED` | 통과 <br> 세션 폐기는 DB로 흉내 냄, 발급 API는 #51 |

| T7 | 탈퇴한 뒤 이전 access 토큰으로 부름 | 401 `UNAUTHORIZED` | 통과 <br> 탈퇴는 DB로 흉내 냄, 탈퇴 API는 #49 |
| T8 | 서명 키를 바꾼 뒤 이전 access 토큰으로 부르고, 프론트엔드 규칙대로 refresh 후 다시 보냄 | 첫 요청 401 `UNAUTHORIZED` <br> refresh 200 <br> 다시 보낸 요청 200 | 미실행 <br> 서버 쪽 첫 요청 401은 `AccessTokenServiceTest`에서 통과, 프론트엔드 흐름은 미실행 |

| T10 | 탭 A가 사용자 A로 글 작성 요청을 보내 401을 받기 전에, 탭 B가 사용자 B로 로그인함 | 탭 A의 refresh 응답 `user.id`가 B라서 작성 요청을 다시 보내지 않음 <br> 글이 B 명의로 저장되지 않음 <br> 탭 A는 B로 화면을 다시 그리고 입력은 남김 (프론트엔드) | 미실행 |
| T11 | T10과 같은 상황에서 조회 요청이 401을 받음 | 조회 요청을 다시 보내지 않음 (프론트엔드) | 미실행 |
| T12 | 만료된 access 토큰과 서명이 틀린 토큰으로 각각 부름 | 둘 다 같은 401 `UNAUTHORIZED` 응답 <br> 만료 여부는 서버 로그에만 남음 | 통과 |
| T13 | 로그인한 브라우저에서 다시 로그인함 (기존 refresh 쿠키가 실림) | 기존 세션이 폐기됨 <br> 기존 세션의 access 토큰은 401 | 통과 |

### 6-6. 동시성

케이스마다 두 작업의 순서를 바꿔 가며 확인한다. 기대는 어느 순서로 끝나도 같아야 한다. ([5-2-QUALITY-CONCURRENCY.md](5-2-QUALITY-CONCURRENCY.md))

| 번호 | 상황 | 기대 | 상태 |
|---|---|---|---|
| CC1 | 일반 로그인의 비밀번호 검증이 끝난 직후 운영진이 그 사람의 비밀번호를 초기화함 | 옛 비밀번호로 만든 세션이 살아 있지 않음 <br> 로그인이 401이거나, 만들어진 세션이 초기화로 폐기됨 | 통과 <br> 검증 직후 초기화되는 순서 <br> 로그인이 먼저 커밋하는 순서는 초기화 API(#51)에서 확인 |
| CC2 | CC1과 같은 순간에 다른 기기에서 비밀번호를 바꿈 | CC1과 같음 | 미실행 |
| CC3 | CC1과 같은 순간에 그 계정이 탈퇴함 | 세션이 남지 않음 | 통과 <br> 탈퇴는 DB로 흉내 냄 |
| CC4 | 같은 사용자가 두 기기에서 같은 지금 비밀번호로 동시에 비밀번호를 바꿈 | 하나만 200, 다른 하나는 400 | 미실행 |
| CC5 | 승인과 거절을 동시에 보냄 | 하나만 성공, 다른 하나는 404나 409 | 미실행 |
| CC6 | 활성 관리자 둘이 동시에 서로의 역할을 `MEMBER`로 내림 | 하나만 성공, 다른 하나는 409 <br> 활성 관리자가 1명 이상 남음 | 미실행 |
| CC7 | 활성 관리자 둘 중 한 명은 탈퇴하고 다른 한 명은 자기 역할을 내림 | 하나만 성공 <br> 활성 관리자가 1명 이상 남음 | 미실행 |
| CC8 | 운영진의 임시 비밀번호 발급 권한 검사 직후 대상이 `STAFF`로 승격됨 | 발급이 403 <br> 대상의 비밀번호와 세션이 바뀌지 않음 | 미실행 |
| CC9 | 서버 두 대가 빈 DB에서 동시에 시작함 | 처음 관리자가 한 명만 생김 | 미실행 |
| CC10 | 같은 이메일로 동시에 가입함 | 하나만 201, 다른 하나는 409 <br> 500이 나지 않음 | 통과 (6-9) |
| CC11 | 관리자 A가 `STAFF`인 X를 `ADMIN`으로 올리는 동안 관리자 B가 X를 `MEMBER`로 내림 | 내리는 쪽은 X가 관리자가 되었으면 마지막 관리자 확인을 거침 <br> 활성 관리자가 1명 이상 남음 | 미실행 |
| CC12 | 임시 비밀번호로 한 번 로그인한 뒤 같은 임시 비밀번호로 다시 로그인 | 401 <br> 일반 로그인 경로로 통과하지 않음 | 통과 |
| CC13 | 관리자가 A 한 명일 때, `MEMBER`인 X의 탈퇴가 역할을 읽은 직후 멈춘 사이 A가 X를 `ADMIN`으로 올리고 자기 역할을 `MEMBER`로 내린 뒤 X의 탈퇴가 진행됨 | X의 탈퇴는 409 <br> X가 활성 관리자로 남아 활성 관리자가 1명 | 미실행 |
| CC14 | 관리자가 A와 X 둘일 때, X의 탈퇴가 관리자 잠금을 잡은 사이 A가 자기 역할을 내림 | X의 탈퇴는 204 <br> A의 강등은 잠금을 기다린 뒤 A가 마지막 관리자라 409 <br> 활성 관리자가 1명 | 미실행 |
