# 1 배경

본 문서는 인증권한 기능에 어떤 백엔드가 왜 필요한지와 이 세트에서 쓰는 용어를 정한다. 기능 범위와 완료 조건은 배경과 사용자 스토리를 따른다. ([BACKGROUND.md](../BACKGROUND.md), [USER-STORIES.md](../USER-STORIES.md))

<br>

### 1-1. 왜 필요한가

게시판과 갤러리의 모든 쓰기 API, 그리고 자유게시판과 자료게시판의 읽기 API는 요청한 사람이 누구이고 어떤 역할인지 알아야 동작한다. 인증권한 백엔드는 이 판단의 근거를 한곳에서 만든다.

- 가입한 사람의 이메일, 이름, 비밀번호 해시와 역할을 저장한다.
- 로그인한 사람에게 토큰을 발급하고, 요청마다 토큰을 검증해 현재 사용자와 역할을 정한다.
- 운영진과 관리자가 가입 승인, 역할 변경, 비밀번호 초기화를 할 수 있게 한다.

다른 기능이 현재 사용자와 역할을 얻는 방법은 3-1에서 정한다. ([3-1-DESIGN-SOFTWARE-ARCHITECTURE.md](3-1-DESIGN-SOFTWARE-ARCHITECTURE.md))

<br>

### 1-2. 관련 정책

| 정책 | 이 세트에 주는 영향 |
|---|---|
| 가입 후 운영진이 승인 (D4) | 가입한 계정은 승인 대기 역할로 시작함 <br> 거절하면 계정을 지움 |
| 메일을 보내지 않음 (D4, PRODUCT.md 3절) | 이메일 소유를 확인하지 않음 <br> 비밀번호 초기화는 운영진이 발급하는 임시 비밀번호로 함 |
| Google 로그인은 MVP 뒤 (D5) | 이메일과 비밀번호 로그인만 만듦 |
| 역할 5단계와 상속 (D6, PRODUCT.md 4절) | 역할을 순서가 있는 값으로 저장하고 높은 역할이 낮은 역할의 권한을 모두 가짐 <br> 승인 대기 회원은 로그아웃과 내 정보를 빼면 방문자와 같음 |
| 마지막 관리자 보호 (D6, USER-STORIES.md 4절, 5절) | 활성 관리자가 한 명이면 그 사람의 역할을 내리거나 탈퇴할 수 없음 |
| 탈퇴해도 글과 앨범은 남김 (USER-STORIES.md 5절) | 탈퇴한 계정의 행은 지우지 않고 개인정보만 지움 |

결정 번호는 제품 결정 기록을 따른다. ([DECISIONS.md](../../DECISIONS.md)) 이 세트의 기술 결정은 세트 결정 기록에 있다. ([DECISIONS.md](DECISIONS.md))

<br>

### 1-3. 용어

| 용어 | 뜻 |
|---|---|
| 역할 코드 | 저장과 API에서 쓰는 역할 값 <br> `PENDING`(승인 대기 회원), `MEMBER`(동아리원), `STAFF`(운영진), `ADMIN`(관리자) <br> 방문자는 로그인하지 않은 상태라서 코드가 없음 |
| 활성 계정 | 탈퇴하지 않은 계정 |
| 활성 관리자 | 역할이 `ADMIN`인 활성 계정 |
| access 토큰 | 요청마다 `Authorization` 헤더로 보내는 짧은 수명의 서명 토큰(JWT) |
| refresh 토큰 | access 토큰을 새로 받을 때만 쓰는 긴 수명의 무작위 문자열 <br> HttpOnly 쿠키로 주고받고 서버는 해시만 저장함 |
| 회전 | refresh 토큰을 쓸 때마다 새 refresh 토큰으로 바꾸는 것 |
| 로그인 세션 | 로그인 한 번으로 생기는 서버 기록 <br> 기기 하나의 로그인 상태에 해당함 <br> 회전으로 이어진 refresh 토큰들과 그 사이 발급한 access 토큰이 모두 여기에 속함 <br> 폐기하면 그 세션의 토큰이 모두 거부됨 |
| 임시 비밀번호 | 운영진이 발급하는 1회용 비밀번호 <br> 유효 시간과 횟수는 USER-STORIES.md 6절을 따름 |
| 비밀번호 변경 필요 상태 | 임시 비밀번호나 처음 관리자 비밀번호로 로그인해서, 비밀번호를 바꾸기 전까지 일부 API만 쓸 수 있는 상태 |
| 익명화 | 탈퇴한 계정의 이메일, 이름, 비밀번호 해시를 지우고 행만 남기는 것 |
